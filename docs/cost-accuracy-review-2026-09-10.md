# 비용 정확도 검토: 캐시 TTL과 보고 비용

검토일: 2026-09-10
대상 소스: `de0eb9f7bfdaa67ba570e0489bc9722c2bb6445b`
입력 자료: 사용자가 제공한 2026-09-09 분석, 워크샵의 사용자 82명·231행 집계

이 문서는 수정 전 소스에 대한 검토 기록이다. 후속 구현 결정은
[ADR-009](decisions/ADR-009-reported-spend-with-computed-diagnostics.md)에 기록한다. 사용자의 최종 지시에 따라
실제 수정은 `costEfficiency.js`와 웹 소비 측으로 한정하고 SQL·가격 계산·롤업을 유지한다.
아래의 서버 표시 필드·로그 정밀도 등 확장 제안은 적용 범위에 포함하지 않는다.

## 판단

**`reported_cost`를 지출 화면의 기본값으로 승격하는 방향을 권고한다.**
다만 이를 실제 청구액으로 명명하거나, 기존 `cost` 필드의 의미를 바꾸면 안 된다.
클라이언트 보고값·TTL 가정에 따른 계산값·청구 확정값을 구분해야 한다.

제공된 이벤트의 차이는 5분 캐시 쓰기를 1시간 단가로 계산하는 현재 코드와 일치한다.
원본 231행과 AWS 청구 자료는 이번 검토에서 확보하지 않았으므로, 이벤트 전체의
재계산·커버리지·실청구 일치는 독립적으로 재검증한 결과가 아니다.

원문에서 수정할 결론은 다음과 같다.

- `$6,640.33`은 **5분 TTL 단가 재계산값**이다. Cost Explorer 대조가 끝나기 전에는
  “AWS 실제 청구액 대비 +17.72%”로 확정하지 않는다.
- “보고 비용은 TTL과 무관하게 정확하다”에는 클라이언트 단가표와 수집 완전성 조건이 필요하다.
  저장소에는 특정 클라이언트 버전의 과소 보고를 기록한 근거가 있다.
- “제품이 내보내는 메트릭은 4개뿐”은 해당 실행에서의 관측이다. 현재 공식 문서는
  8개 메트릭을 나열하며, 이 저장소의 Collector도 그 8개를 허용한다.
- “OTel로 TTL 수집은 불가능”은 너무 강하다. 기본 `token.usage`에는 TTL 차원이 없지만,
  현재 공식 문서는 요청·응답 본문 로그를 선택적으로 내보내는 경로를 설명한다.
  해당 기능이 현장의 2.1.263/2.1.266에서 같은 방식으로 동작하는지는 별도 실측 대상이다.
- 기존 비용 합계를 화면에 표시하는 데에는 SQL을 바꾸지 않아도 된다. 하지만 누락·부분 수집을
  식별하는 품질 정보까지 제공하려면 현재 집계 결과만으로는 충분하지 않다.

## 1. 확인한 가격과 차액

현재 [pricing.js](../dashboard/server/pricing.js)의 기본값은
`PRICING_CACHE_WRITE_TTL=1h`이다. `withComputedCost()`와 `tierCosts()`는
모델·그룹·요청 종류에 관계없이 그 전역 설정을 사용한다.

| 모델 | 입력 | 출력 | 캐시 읽기 | 쓰기 5분 | 쓰기 1시간 | 쓰기 1M개당 차액 |
|---|---:|---:|---:|---:|---:|---:|
| claude-opus-5 | 5 | 25 | 0.50 | 6.25 | 10 | 3.75 |
| claude-sonnet-5 | 2 | 10 | 0.20 | 2.50 | 4 | 1.50 |
| claude-haiku-4-5 | 1 | 5 | 0.10 | 1.25 | 2 | 0.75 |

단위는 USD/1M tokens. 이 값은 현재 소스에서 읽고, 캐시 쓰기만 1M인 입력을
`withComputedCost()`에 넣어 확인했다. Anthropic 공식 가격표도 이 세 모델의 값을
일치하게 명시한다. Sonnet 5의 $2/$10은 현재 표준 가격으로 안내되어 있다.[S2]

```text
TTL에 의한 계산 차액
  = Σ모델(cache_write_tokens / 1,000,000 × input_price × 0.75)
```

제공된 합계를 센트 단위 정수로 검산한 결과:

| 비교 | 차액 | 상대 차이 |
|---|---:|---:|
| 계산 비용 7,817.28 − 5분 재계산 6,640.33 | 1,176.95 | +17.72427% |
| 보고 비용 6,647.79 − 5분 재계산 6,640.33 | 7.46 | +0.11234% |
| 계산 비용 7,817.28 − 보고 비용 6,647.79 | 1,169.49 | +17.59216% |

따라서 **`cost`와 `reported_cost`의 괴리는 17.59%**다. 17.72%는 5분 재계산값을
분모로 쓴 수치다. 경고 지표에는 어떤 비교와 분모를 사용했는지 명시해야 한다.
잔차 $7.46의 원인은 미확정이며 반올림 때문이라고 단정하지 않는다.

## 2. 서로 다른 TTL과 집계 조건

| 항목 | 현재 동작 | 비용 검토에 미치는 영향 |
|---|---|---|
| Bedrock 프롬프트 캐시 TTL | 지원 모델에서 TTL 미지정 시 5분, 명시하면 1시간 사용 가능 [S1] | 쓰기 단가가 달라진다. |
| 대시보드 가격 계산의 TTL 가정 | 전역 `1h`, 환경변수로 `5m` 선택 가능 | 실제 TTL을 관측하거나 Claude Code 설정을 변경하는 기능이 아니다. |
| Express API 응답 캐시 | `index.js`의 `CACHE_TTL_MS=320_000` | 이미 계산된 응답을 재사용한다. 데이터 반영 지연을 만들 수 있다. |
| 프런트 조회 시각 | `useApi.js`의 120초 경계·150초 유예 | 요청 상한이 현재보다 약 150~270초 이전이다. 롤업의 실제 포함 범위는 별도다. |
| ClickHouse 보존 TTL | 원시·롤업 데이터의 보존/이동 정책 | 보존 기간 밖 조회의 누락과 관련된다. 프롬프트 캐시 가격과는 독립적이다. |

API 응답 캐시를 비우거나 TTL을 줄이는 조치만으로는 이 단가 차이가 해결되지 않는다.
과거의 고정된 조회 구간에서도 같은 토큰에 같은 1시간 단가가 적용되기 때문이다.

[queries.js](../dashboard/server/queries.js)의 `TOKEN_SUMS`는 `incFlat()`이 계산한
증가량을 합산한다. 원시 `otel_metrics_sum.Value`를 직접 합산하는 SQL로 교체하면
누적 카운터가 중복 집계된다. 비용 기준을 바꿔도 이 처리와 migration-003의
프로세스 세그먼트 구분은 유지해야 한다.

추가 대조 시 다음 조건을 고정한다.

- UTC 기준 `[from, to)`와 그룹·모델·사용자 필터.
- `costSummary`의 미분류 포함과 `costByUserModel`의 기본 미분류 제외·이메일 없는 행 제외.
- 4시간 초과 조회의 시간별 롤업 경계 처리와, 원시 로그의 정확한 시간 경계 차이.
- 재시작 세그먼트, 수집 지연·중단, 조회 시작 이전 3일 lookback 밖의 기준값 유실 가능성.

이 조건들은 코드에 존재하는 추가 오차 요인이다. 이번 이벤트에서 실제로 기여한
비중은 확인되지 않았다.

## 3. `reported_cost`의 품질과 TTL 관측 가능성

### 보고 비용

저장소의 `queries.js`·`CHANGELOG.md`에는 2.1.251이 `claude-fable-5-1`을
opus-5 가격으로 계산하여 약 절반을 보고했고, 2.1.258에서는 달라졌다는 조사 기록이 있다.
이번 검토에서 그 바이너리나 과거 청구서를 다시 검증한 것은 아니다. 그러나 모든 버전·모델에
보고값의 정확성을 일반화할 수 없다는 운영 근거로는 보존해야 한다.

현재 `/api/reliability/reported-vs-computed`는 `AppVersion × model × group`별
API 로그의 보고 비용과 계산 비용을 비교한다. 이 진단을 유지하되 다음을 보완한다.

- 1시간 단가와의 차이만으로 클라이언트 오류를 판정하지 않는다.
- **5분·1시간 계산값을 함께** 제공하고, 그 사이에 있는 값은 혼합 TTL로 설명 가능한
  범위로 표시한다. 범위 안이라는 사실만으로 정확한 수집이나 TTL을 입증하지는 못한다.
- 범위 밖이면 버전별 가격, 지역별 가격, 누락·중복, 필터와 시간 경계를 추가 조사한다.
- 현재 로그 쿼리는 `cost_usd`만 읽는다. 정밀도 대조를 위해 `cost_usd_micros`의 존재와
  유효성을 확인하고, 있을 때 `/1e6`, 없을 때 `cost_usd`를 사용하는 방식을 검토한다.
  두 필드를 합산하지 않는다.

`reported_cost > 0`인 사용자 100%는 **사용자별 보고값의 존재**를 입증한다.
각 사용자의 모든 요청 비용이 수집되었다는 의미는 아니다. 현재 `sumIf` 결과의 `0`만으로는
실제 0과 해당 비용 메트릭의 미수집을 구분할 수 없다. 사용자·세션·모델별로 기간 내
보고 시계열과 토큰 시계열의 존재·기간을 대조하고, 집계 전에 품질 정보를 남겨야 한다.
누락 여부를 확인하지 않은 `reported_cost || cost` 폴백은 사용하지 않는다.

### 기본 메트릭과 본문 로그

현재 공식 문서의 `token.usage`는 `input`, `output`, `cacheRead`, `cacheCreation`
유형을 제공하며 TTL별 토큰 필드는 설명하지 않는다.[S3]
이미 저장된 이 네 토큰 합계만으로 5분·1시간 비중을 정확히 복원할 수 없다는
원문의 핵심 판단은 타당하다.

다만 같은 문서는 `OTEL_LOG_RAW_API_BODIES`로 `api_request_body`와
`api_response_body`를 내보낼 수 있다고 설명한다. 응답 본문에는 `usage`가 포함된다.
따라서 **원시 응답의 TTL별 usage를 추출하는 별도 수집 경로는 검토 가능**하다.
문서만으로 현장 버전의 Bedrock 응답에 그 필드가 보존되는지까지 확인된 것은 아니다.[S3]

이 경로는 자동으로 켜지 않았다. 원시 본문에는 대화 내용이 포함되고 inline 모드는
기본 60KB에서 잘릴 수 있다. 현재 [collector-config.yaml](../collector-config.yaml)은
`prompt`, `prompt_text`만 제거하므로 `body` 전체는 그대로 저장될 수 있다.
시험한다면 로컬에서 필요한 usage·TTL 필드만 추출하고 본문을 폐기하는 처리가 선행되어야 한다.
이 작업을 보고 비용 표시 전환의 선행 조건으로 삼을 필요는 없다.

`promptCacheTtl`·`subagentPromptCacheTtl`의 공급자별 기본값과 워크샵 CFN 변경은
제공된 실측 자료에 근거한다. 이번에 조회한 공식 settings 페이지에는 두 키가
명시되지 않았으므로 독립 확인으로 표시하지 않는다.

## 4. 수정 제안과 영향 범위

### 필드와 표시 정책

| 값 | 권고 의미 |
|---|---|
| 기존 `cost`, summary의 `computed_cost` | 기존 토큰 × 가격표 추정값 유지. TTL 가정을 표시한다. |
| `reported_cost`, `prev_reported_cost` | 클라이언트 보고 비용. 지출 화면과 기간 비교의 기본값으로 사용한다. |
| 미수집·부분 수집 상태 | 0달러로 표시하지 않는다. 추정값을 대체 표시한다면 출처와 불완전성을 명시한다. |
| 실제 청구 비용 | Cost Explorer/CUR 대조로 확인한 별도 값. Enterprise는 해당 공급자 정산과 대조한다. |
| 캐시 티어별 비용 | 토큰 계산 추정값. 보고 비용의 실제 구성비라고 표시하지 않는다. |

`unpriced`는 **서버 가격표 부재**를 뜻한다. 그 모델의 보고 비용이 유효한데도 행을
제외하거나 보고 비용 기반 효율 지표를 무효화하면 안 된다. 계산값의 미산정과 보고값의
미수집·신뢰도는 별도 상태로 관리한다.

화면마다 임의로 폴백하지 않도록 공통 비용 선택 정책을 두고, 필터·순위·합계·비율·CSV가
모두 같은 선택 결과를 사용하도록 한다. 기존 `cost`를 보고값으로 덮어쓰면 Reliability의
`reported_cost / cost`가 항상 1이 되는 회귀가 생긴다.

Usage의 프로젝트·진입점·스킬 비용과 Reliability의 버전별 비용은 이미 보고 비용을
사용하는 경로다. 같은 의미의 라벨을 사용하되 중복 변환하지 않는다.

## 5. 배포본과 tarball 확인 결과

Sonnet 5의 $3/$15 → $2/$10 변경은 `0654c6d29579866aeb60929888481de687081cc4`
(2026-09-02)에 들어갔다.

별도 워크샵 저장소의 로컬 배포 인계 자료는
main 커밋 `ed7919950caf6c73d5bdfa8d8aac99e520613156`과
`cc-ab-dashboard:20260905-131041`을 연결하며 다음 값을 기록한다.

```text
크기: 61,969,752 bytes
MD5: f5047d53787c951a2573702ff6f42850
RepoTag: 1개
```

그 커밋과 현재 HEAD의 `dashboard/server/pricing.js`는 동일하다.

```text
SHA-256: 7244945a42ac2ad45e3d6f6708688a60607878901dc2add6c1108b510c36d23f
Sonnet 5 기본값: input=2, output=10
```

이는 **배포용으로 기록된 소스의 기본값**을 확인하는 근거다. 실제 tarball의 내용,
실행 중인 이미지 digest, `PRICING_JSON`/`PRICING_CACHE_WRITE_TTL` 적용값은 이번에
조회하지 않았다. 실제 배포 설정의 확정 근거로 확대하지 않는다.

이 저장소에는 `assets/cc-dashboard-arm.tar.gz`와 `docs/INFRA.md`가 없다.
인계 스크립트도 별도 워크샵 콘텐츠 저장소를 대상으로 한다. 따라서 해당 tarball의
갱신은 워크샵 저장소에서 수행할 작업이다.

재발 방지를 위해 릴리스마다 Git 커밋·이미지 digest·tarball SHA-256·실행 이미지 ID를
연결한 manifest를 남기고, 그 이미지에서 내보낸 tarball을 워크샵에 배포한다.
`PRICING_JSON`의 가격 자체를 공개 API에 노출할 필요는 없다. 운영 검증에는
적용 여부와 내부 설정 fingerprint를 활용할 수 있다.

## 6. 검증 결과와 적용 전 확인 항목

이번 검토에서 수행한 검증:

```bash
cd dashboard/server
node --test pricing.test.js pricing.ttl5m.test.js costEfficiency.test.js queries.test.js
```

4개 테스트 파일 모두 통과했다. 이는 현재 동작에 대한 검증이며 수정 구현의 통과 결과가 아니다.
추가 in-memory assertion으로 세 모델의 1M 캐시 쓰기 가격과 TTL 차액, 제공된 세 합계의
산술 관계를 확인했다.

구현 시 필요한 검증은 다음과 같다.

1. 동일한 범위에서 보고 비용 합계가 모든 지출 화면·기간 비교·CSV·효율 지표에 일관되게
   사용되고, 계산값과 Reliability의 비교 비율은 보존되는지 확인한다.
2. 보고값 0·누락·부분 수집, 미등록 모델의 양수 보고값, LOC/commit=0,
   두 그룹을 오간 사용자, 비용 API 실패를 검증한다.
3. 30개를 초과하는 Agent 데이터에서 보고 비용 상위 항목이 서버 절단으로 사라지지 않는지,
   계산값 순위와 보고값 순위가 다를 때 UI/CSV가 일치하는지 확인한다.
4. 5분·1시간·혼합 TTL과 버전별 가격 차이가 있는 데이터를 비교한다. 그레인이 다른
   summary·사용자·로그 합계를 동일한 모집단이라고 가정하지 않는다.
5. 워크샵 원본 231행을 확보해 4자 비교를 다시 실행한다. Bedrock 사용자 범위와 청구 대상
   계정·UTC 날짜·사용 유형을 맞춘 CE/CUR 자료로 최종 대조한다. Enterprise 비용을
   AWS Bedrock 청구액에 합쳐 비교하지 않는다.
6. CFN 변경의 머지·배포 시점과 기존 세션 반영을 확인한다. 설정 변경일만으로 전체 트래픽이
   1시간 TTL로 전환되었다고 가정하지 않는다.

애플리케이션 코드, Collector 설정, 배포 이미지, 워크샵 tarball은 이번 검토에서 변경하지 않았다.

## 7. 별도 개선 대상: 지역별 단가

`pricing.js`는 지역 접두사를 정규화해 제거하고 모든 추론 프로파일에 같은 단가를 적용한다.
공식 Anthropic 문서는 Claude 4.5 이후 모델의 Bedrock 지역 엔드포인트에 global 대비
가격 차이가 있음을 설명한다.[S2] 따라서 이 계산을 여러 배포 환경에 일반화하려면
가격 산정 전에 추론 지역 유형을 보존하고 해당 AWS SKU를 확인해야 한다.
원문이 제시한 테스트 모델은 `global.*`이며, 이 문제를 이번 차액의 원인으로 확인한 것은 아니다.
