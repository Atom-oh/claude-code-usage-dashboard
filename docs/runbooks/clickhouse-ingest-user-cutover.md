# English

## Overview
`infra/clickhouse.tf` now defines an `otel_ingest` account whose privileges are
`INSERT ON claude_code.*` plus `SELECT ON claude_code.otel_metrics_sum`, and `user-data.sh`
points newly launched collector instances at it. `otel_writer` — the previous collector
account, which has no explicit grants and therefore full privileges (table functions, the
`system` database, DDL/DROP) — stays in place, because the schema-init Job and the daily
backup CronJob both still authenticate as it.

## When to Use
- Before launching a new workshop fleet after this change has been applied
- Any time the `otel_ingest` password is rotated

## Prerequisites
- `terraform` in `infra/`, with the usual variables already set
- `kubectl` context `fsi-demo-cluster`, access to namespace `claude-code`
- `aws` CLI with `ssm:PutParameter` and `kms:Encrypt` on the parameter's KMS key

## Procedure

### 1. Apply the account
```bash
cd infra
terraform apply -var="clickhouse_ingest_password=<PUT-THE-GENERATED-PASSWORD-HERE>"
```
The password must be generated by the operator beforehand (e.g. `openssl rand -base64 32`).
It must never be pasted into a committed file, a shell history line that gets shared, or a
runbook.

### 2. Create the SSM parameter out of band
Terraform does not manage this parameter, exactly like the existing writer parameter:
```bash
aws ssm put-parameter \
  --name /claude-code/ab/clickhouse-ingest-password \
  --type SecureString \
  --value '<PUT-THE-GENERATED-PASSWORD-HERE>' \
  --region ap-northeast-2
```
This must be the same value passed to `terraform apply` in step 1. The instance profile needs
`ssm:GetParameter` + `kms:Decrypt` on this parameter — the existing profile already has this
for the writer parameter, so check that its resource ARN pattern also covers this new
parameter name before relying on it.

### 3. Verify the account inside the cluster
This step is mandatory: the grants are rendered from Terraform through the ClickHouse
operator's user config and had not been applied against a live cluster when this runbook was
written.
```bash
kubectl --context fsi-demo-cluster -n claude-code exec chi-cc-ab-replicated-0-0-0 \
  -c clickhouse -- clickhouse-client -q "SHOW GRANTS FOR otel_ingest"
```
It must print **both** lines:
```
GRANT INSERT ON claude_code.* TO otel_ingest
GRANT SELECT ON claude_code.otel_metrics_sum TO otel_ingest
```
If only the `INSERT` line appears, the second grant did not render — **stop here**. Ingestion
will fail with `Code: 497 … ACCESS_DENIED` on every insert, because the materialized view onto
`otel_metrics_sum` is checked with the inserting user's privileges. The fix in that case is to
express the account as a `users.d/*.xml` entry in the installation's `files` map with two
`<query>` children instead of a list value — this was verified to work on ClickHouse 24.8.

### 4. New instances only
`user-data.sh` is a cloud-init template, so this cutover only affects **newly launched**
instances. Running workshop instances are deliberately **not** modified — the existing fleet
keeps using `otel_writer` until it is re-provisioned, and that is the accepted end state, not
a pending task. Do not edit `/etc/otelcol/env` on a live instance.

### 5. After the last `otel_writer` instance is gone
Only once no collector instance is still authenticating as `otel_writer`, consider removing
its reachability from the ingest path (it is IP-allowlisted to `10.0.0.0/8` in
`infra/clickhouse.tf`). This is a follow-up, not part of this cutover. Do not delete
`otel_writer` itself — the schema-init Job and the backup CronJob still use it.

## Verification
- [ ] `SHOW GRANTS FOR otel_ingest` prints both the `INSERT` and `SELECT` lines shown in step 3
- [ ] A freshly launched instance's `/etc/otelcol/env` has `CH_USER=otel_ingest` (the file is
      mode `600`, so reading it needs root — do not print the file's contents into a shared
      terminal)
- [ ] `systemctl status otelcol.service` is active on that instance
- [ ] `SELECT max(TimeUnix) FROM claude_code.otel_metrics_sum` advances after the instance runs
      Claude Code
- [ ] The rollup also advances (`SELECT max(hour) FROM claude_code.otel_metrics_sum_hourly`),
      which is what proves the materialized view fired under the narrower account
- [ ] `sudo grep -c 'CH_PASSWORD=' /var/log/cloud-init-output.log` on that instance returns `0`
      (the traced assignment is what the xtrace guard removes; the heredoc body was never
      traced)

## Rollback
Revert `CH_USER` and `CH_PASSWORD_SSM_PARAM` in `user-data.sh` to `otel_writer` and its
parameter (`/claude-code/ab/clickhouse-writer-password`), then re-provision. `otel_ingest` can
be left in place — it is inert if nothing authenticates as it.

## Notes
- `otel_ingest`'s two grants were measured on `clickhouse/clickhouse-server:24.8.14.39`: an
  INSERT-only account cannot insert into a table that has a materialized view created without
  an explicit security clause, because the view's `SELECT` is checked against the inserting
  user; the minimal fix is `SELECT` on the source table only.
- Last verified: 2026-09-02

# 한국어

## 개요
`infra/clickhouse.tf`는 이제 `INSERT ON claude_code.*`와
`SELECT ON claude_code.otel_metrics_sum` 권한을 가진 `otel_ingest` 계정을 정의하고,
`user-data.sh`는 새로 띄우는 컬렉터 인스턴스를 이 계정으로 연결한다. 이전 컬렉터 계정이던
`otel_writer`는 명시적 grants가 없어 기본 전체권한(테이블 함수·`system` 데이터베이스·
DDL/DROP)을 갖는데, 그대로 남는다 — 스키마 초기화 Job과 일별 백업 CronJob이 여전히 이
계정으로 접속하기 때문이다.

## 사용 시점
- 이 변경이 적용된 뒤 새 워크숍 플릿을 띄우기 전
- `otel_ingest` 비밀번호를 교체할 때마다

## 사전 요구 사항
- `infra/`에서 실행하는 `terraform`, 기존 변수는 이미 설정되어 있음
- `kubectl` context `fsi-demo-cluster`, `claude-code` 네임스페이스 접근 권한
- 해당 파라미터의 KMS 키에 대한 `ssm:PutParameter`, `kms:Encrypt` 권한을 가진 `aws` CLI

## 절차

### 1. 계정 적용
```bash
cd infra
terraform apply -var="clickhouse_ingest_password=<PUT-THE-GENERATED-PASSWORD-HERE>"
```
비밀번호는 운영자가 사전에 직접 생성해야 한다(예: `openssl rand -base64 32`). 이 값은
커밋되는 파일이나 공유되는 쉘 히스토리 줄, 런북 등 어디에도 붙여넣으면 안 된다.

### 2. SSM 파라미터를 별도로 생성
이 파라미터는 기존 writer 파라미터와 마찬가지로 terraform이 관리하지 않는다:
```bash
aws ssm put-parameter \
  --name /claude-code/ab/clickhouse-ingest-password \
  --type SecureString \
  --value '<PUT-THE-GENERATED-PASSWORD-HERE>' \
  --region ap-northeast-2
```
이 값은 1단계의 `terraform apply`에 넘긴 값과 반드시 같아야 한다. 인스턴스 프로파일은 이
파라미터에 대해 `ssm:GetParameter` + `kms:Decrypt` 권한이 필요하다 — 기존 프로파일은 writer
파라미터에 대해 이미 이 권한을 가지고 있으므로, 그 리소스 ARN 패턴이 이 새 파라미터 이름도
커버하는지 먼저 확인하라.

### 3. 클러스터 안에서 계정 검증
이 단계는 필수다: grants는 Terraform에서 ClickHouse 오퍼레이터의 유저 설정으로 렌더링될
뿐, 이 런북을 작성할 시점에는 실 클러스터에 적용된 적이 없었다.
```bash
kubectl --context fsi-demo-cluster -n claude-code exec chi-cc-ab-replicated-0-0-0 \
  -c clickhouse -- clickhouse-client -q "SHOW GRANTS FOR otel_ingest"
```
**두 줄** 모두 출력돼야 한다:
```
GRANT INSERT ON claude_code.* TO otel_ingest
GRANT SELECT ON claude_code.otel_metrics_sum TO otel_ingest
```
`INSERT` 줄만 나온다면 두 번째 grant가 렌더링되지 않은 것이다 — **여기서 멈춘다**. 이 상태로
가면 모든 insert가 `Code: 497 … ACCESS_DENIED`로 실패한다. `otel_metrics_sum`에 걸린
materialized view의 `SELECT`가 insert하는 유저의 권한으로 검사되기 때문이다. 이 경우의
해결책은 이 계정을 list 값 대신 `<query>` 자식 두 개를 가진 `users.d/*.xml` 항목(installation의
`files` 맵)으로 표현하는 것이다 — ClickHouse 24.8에서 동작함을 확인했다.

### 4. 신규 인스턴스에만 적용
`user-data.sh`는 cloud-init 템플릿이므로 이 전환은 새로 띄우는 인스턴스에만 적용된다.
운영 중인 워크숍 인스턴스는 의도적으로 건드리지 않는다 — 기존 플릿은 재프로비저닝되기 전까지
계속 `otel_writer`를 쓰며, 이는 남아 있는 작업이 아니라 받아들여진 최종 상태다. 살아있는
인스턴스에서 `/etc/otelcol/env`를 수정하지 마라.

### 5. 마지막 `otel_writer` 인스턴스가 사라진 뒤
`otel_writer`로 접속하는 컬렉터 인스턴스가 하나도 남지 않았을 때에만, 수집 경로에서 이
계정의 접근 가능성을 제거하는 것을 고려한다(`infra/clickhouse.tf`에서 `10.0.0.0/8`로
IP 허용목록이 걸려 있다). 이건 이 전환의 일부가 아니라 후속 작업이다. `otel_writer` 계정
자체는 삭제하지 마라 — 스키마 초기화 Job과 백업 CronJob이 여전히 사용한다.

## 검증
- [ ] `SHOW GRANTS FOR otel_ingest`가 3단계에 나온 `INSERT`·`SELECT` 두 줄을 모두 출력한다
- [ ] 새로 띄운 인스턴스의 `/etc/otelcol/env`에 `CH_USER=otel_ingest`가 있다(파일 권한이
      `600`이라 읽으려면 root 권한이 필요하다 — 공유 터미널에 파일 내용을 그대로 출력하지
      말 것)
- [ ] 해당 인스턴스에서 `systemctl status otelcol.service`가 active다
- [ ] 해당 인스턴스에서 Claude Code를 실행한 뒤
      `SELECT max(TimeUnix) FROM claude_code.otel_metrics_sum`이 진행된다
- [ ] 롤업도 진행된다(`SELECT max(hour) FROM claude_code.otel_metrics_sum_hourly`) — 이는 더
      좁아진 계정 아래에서도 materialized view가 실제로 동작했음을 증명한다
- [ ] 해당 인스턴스의 `/var/log/cloud-init-output.log`에서
      `sudo grep -c 'CH_PASSWORD=' /var/log/cloud-init-output.log`가 `0`을 반환한다(트레이스된
      대입문이 xtrace 가드가 없애는 대상이며, heredoc 본문은 원래부터 트레이스되지 않는다)

## 롤백
`user-data.sh`의 `CH_USER`, `CH_PASSWORD_SSM_PARAM`을 `otel_writer`와 그 파라미터
(`/claude-code/ab/clickhouse-writer-password`)로 되돌린 뒤 재프로비저닝한다. `otel_ingest`는
그대로 남겨둬도 된다 — 아무도 이 계정으로 인증하지 않으면 그냥 비활성 상태로 남는다.

## 참고
- `otel_ingest`의 grant 두 줄은 `clickhouse/clickhouse-server:24.8.14.39`에서 실측했다:
  명시적 보안절 없이 만들어진 materialized view가 걸린 테이블에는 INSERT 전용 계정이 insert할
  수 없다 — view의 `SELECT`가 insert하는 유저의 권한으로 검사되기 때문이다. 최소한의 해결책은
  소스 테이블에 대한 `SELECT`뿐이다.
- 최종 검증일: 2026-09-02
