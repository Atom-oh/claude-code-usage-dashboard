Claude Code + Codex · 설치

전체 서비스 빌드 및 배포

Git 소스에서 시작하세요. 코딩 클라이언트를 연결하기 전에 대시보드, ClickHouse와 스키마, OTel 수집 경로를 배포하세요.

2026년 11월 10일 업데이트 · 소스 기반 안내입니다. 선택한 릴리스와 대상 환경을 확인하세요.

복제 및 빌드 · 데이터베이스 스키마 · OTel 백엔드 · 호스팅 옵션 · 클라이언트 트레이스

설치해야 하는 항목

이 안내서는 게시된 애플리케이션 .tar.gz 파일에 의존하지 않습니다. 저장소를 복제하고 Docker 이미지를 빌드하세요. 선택적 장치 패키지는 설치된 대시보드에서 생성되며 백엔드를 설치하지 않습니다.

구성 요소용도 및 출처
대시보드 애플리케이션dashboard/Dockerfile은 React와 Express를 단일 이미지로 빌드하고, 포트 8080에서 UI와 API를 제공합니다. ClickHouse나 OTel Collector를 실행하지 않습니다.
ClickHouse 및 스키마영구 데이터베이스, 텔레메트리 테이블, 머티리얼라이즈드 뷰 및 마이그레이션 원장입니다. 배포에 맞는 단일 노드 또는 복제 스키마를 선택하세요.
OTel Collector별도로 실행되는 Collector가 로그, 메트릭 및 트레이스를 수신하고 저장소의 필터와 변환을 적용한 다음 준비된 테이블에 기록합니다.
인증 및 보안 정보OIDC 또는 설정된 Basic 인증, HTTPS 액세스, 비공개 데이터베이스 연결, 별도의 읽기/수집/관리 자격 증명 및 보호된 보안 정보 마운트입니다.
클라이언트 수집Claude Code/Codex 내보내기 도구와 로컬 Collector 또는 조직 관리 수집 경로입니다. 백엔드 배포로 사용자의 클라이언트 설정이 변경되지는 않습니다.

먼저 Git과 buildx가 포함된 Docker를 설치하세요. EKS의 경우 조직 배포 사전 요구 사항에 설명된 기존 클러스터 종속 항목, Terraform, AWS CLI 및 kubectl도 준비하세요.

1. 릴리스를 복제하고 이미지 빌드

CCDASH_RELEASE를 실제로 게시된 vX.Y.Z 릴리스 태그로 설정하세요. 런타임에 맞는 플랫폼을 선택하세요. 제공된 EKS 배포는 linux/arm64를 사용합니다.

: "${CCDASH_RELEASE:?Set a published vX.Y.Z release tag}"
CCDASH_PLATFORM=linux/arm64
git clone https://github.com/Atom-oh/claude-code-usage-dashboard.git
cd claude-code-usage-dashboard
git checkout --detach "$CCDASH_RELEASE"
CCDASH_REVISION=$(git rev-parse HEAD)
docker build --platform "$CCDASH_PLATFORM" \
  --build-arg APP_REVISION="$CCDASH_REVISION" \
  --tag "ccdash:$CCDASH_RELEASE" dashboard

빌드 컨텍스트는 저장소 루트가 아니라 dashboard/입니다. x86 런타임이라면 linux/amd64를 선택하고 해당 배포를 별도로 검증하세요. 다른 아키텍처에서 빌드하려면 크로스 플랫폼 빌더를 구성해야 합니다.

프로덕션에서는 검토된 빌드, 검사, 레지스트리 게시 및 롤아웃 절차를 따르세요. 릴리스, 소스 리비전 및 이미지 다이제스트를 보존하세요. 로컬 빌드 성공을 배포 완료로 간주하지 마세요.

2. 수집을 시작하기 전에 ClickHouse 준비

먼저 영구 ClickHouse 저장소와 백업/복구를 구성하세요. 읽기 전용 대시보드 계정, 필요한 내보내기 권한이 있는 수집 계정, 관리용 마이그레이션 계정을 만드세요. 스키마 파일은 프로덕션 사용자를 구성하지 않습니다.

제공된 계정 정책은 otel_reader에 claude_code.*에 대한 SELECT 권한을 부여합니다. 머티리얼라이즈드 뷰의 원본 읽기를 위해 otel_ingest 계정에는 claude_code.*에 대한 INSERT와 claude_code.otel_metrics_sum에 대한 SELECT가 필요합니다. INSERT만 부여하면 수집이 실패할 수 있습니다. 계정 네트워크를 제한하고 저장소의 ClickHouse 계정 정책을 참고해 보호된 자격 증명을 구성하세요.

배포 유형스키마 경로
새 단일 노드 / 로컬 평가clickhouse-schema.sql: 비복제 테이블, 뷰, 롤업 및 현재 마이그레이션 가드입니다. Claude 텔레메트리와 Codex 전용 메트릭/비용/진단 테이블이 포함됩니다.
새 복제 EKS 설치infra/files/clickhouse-schema-replicated.sql과 생성된 계약 및 infra/schema.tf의 스키마 초기화 Job을 사용합니다. 선언된 클러스터/Keeper 토폴로지와 예상 복제본이 필요합니다.
기존 설치테이블, 원장 및 과거 데이터를 검사하세요. 런북에 따라 필요한 번호 지정 마이그레이션만 적용하세요. 부트스트랩을 업그레이드처럼 다시 실행하지 마세요.

EC2/Docker에서는 먼저 전용 브리지 네트워크와 영구 데이터 볼륨을 만드세요. 익명 기본 액세스가 없고 네트워크가 제한된 reader/ingest/admin 계정을 포함하는 보호된 users.d XML과 관리자 클라이언트 구성을 준비하세요. 선택한 릴리스에 맞는 ClickHouse 이미지를 검증하고 고정하세요. 로컬 Compose 버전은 출발점으로 참고할 수 있습니다. CLICKHOUSE_SKIP_USER_SETUP=1은 준비된 계정 구성을 유지합니다. 먼저 인증과 네트워크 제한을 검증하세요. 다음 명령은 데이터베이스 포트를 공개하지 않고 시작합니다.

: "${CCDASH_NETWORK:?Set the prepared private Docker network}"
: "${CCDASH_CH_CONTAINER:?Set the ClickHouse container name}"
: "${CCDASH_CH_IMAGE:?Set the reviewed ClickHouse image including its sha256 digest}"
: "${CCDASH_CH_DATA_VOLUME:?Set the prepared persistent data volume}"
: "${CCDASH_CH_USERS_DIR:?Set the protected users.d configuration directory}"
: "${CCDASH_CH_ADMIN_CONFIG:?Set the protected admin client configuration file}"
docker run -d --name "$CCDASH_CH_CONTAINER" --restart unless-stopped \
  --network "$CCDASH_NETWORK" --network-alias clickhouse.internal \
  --env CLICKHOUSE_SKIP_USER_SETUP=1 \
  --mount "type=volume,src=$CCDASH_CH_DATA_VOLUME,dst=/var/lib/clickhouse" \
  --mount "type=bind,src=$CCDASH_CH_USERS_DIR,dst=/etc/clickhouse-server/users.d,readonly" \
  --mount "type=bind,src=$CCDASH_CH_ADMIN_CONFIG,dst=/run/ccdash-admin/client.xml,readonly" \
  "$CCDASH_CH_IMAGE"

ClickHouse가 시작될 때까지 기다린 뒤 마운트한 관리자 클라이언트 구성으로 인증하세요. 아래 스키마 명령에서 컨테이너 경로는 /run/ccdash-admin/client.xml입니다. 이 네트워크에서 앱과 Collector의 데이터베이스 호스트로 clickhouse.internal을 사용하세요. 이미지와 마운트한 구성은 런타임 아키텍처 및 파일 읽기 권한과 일치해야 합니다.

새 빈 비복제 데이터베이스의 경우, 실행 중인 ClickHouse 컨테이너 이름을 CCDASH_CH_CONTAINER에, 보호된 관리자 클라이언트 구성의 컨테이너 내부 경로를 CCDASH_CH_CLIENT_CONFIG에 설정하세요. 영구 저장소를 /var/lib/clickhouse에 마운트하고 수집을 열기 전에 사용자를 구성하세요. 포트 8123/9000은 비공개로 유지하세요. 아래에는 비밀번호가 포함되어 있지 않습니다.

: "${CCDASH_CH_CONTAINER:?Set the prepared ClickHouse container name}"
: "${CCDASH_CH_CLIENT_CONFIG:?Set the mounted admin client configuration path}"
docker exec -i "$CCDASH_CH_CONTAINER" \
  clickhouse-client --config-file "$CCDASH_CH_CLIENT_CONFIG" \
  --multiquery < clickhouse-schema.sql

docker exec "$CCDASH_CH_CONTAINER" clickhouse-client \
  --config-file "$CCDASH_CH_CLIENT_CONFIG" \
  --query "SELECT name FROM system.tables WHERE database='claude_code' ORDER BY name"

otel_logs, otel_traces, Claude 메트릭 테이블, Codex 메트릭 테이블 4개, 뷰 및 schema_migrations를 확인하세요. Collector는 create_schema: false를 사용하므로 누락된 테이블을 만들 수 없습니다. 마이그레이션 003에서는 롤업을 SQL 문 단위로 전환해야 합니다. 타입 지정 읽기를 활성화하려면 테이블 존재 여부만으로는 부족하며 과거 및 실시간 데이터 범위도 검증해야 합니다.

기존 dashboard/docker-compose.yml은 새 로컬 ClickHouse 볼륨과 합성 시드 데이터를 초기화합니다. 개발용 인증을 사용하며 OTel Collector 서비스는 없습니다. 이는 평가를 위한 출발점이지 완전한 프로덕션 설치가 아니며, 기존 볼륨은 다시 초기화되지 않습니다.

스키마 수명 주기 및 마이그레이션 순서 · Codex 비용 읽기 활성화

3. OTel 백엔드 설치

ClickHouse 내보내기 도구와 필요한 프로세서를 포함하는 Collector 배포판을 실행하세요. 선택적 장치 토큰 경로의 경우 dashboard/collector/generated/central.yaml은 저장소의 비공개 중앙 수신기 정책입니다. infra/device_ingest.tf에 정의된 검토 및 다이제스트 고정 Contrib 이미지를 사용하세요.

  1. 중앙 YAML을 Collector 구성으로 마운트하세요. CH_HOST, CH_PORT(네이티브 포트), CH_DB=claude_code, CH_USER 및 이에 맞는 CLAUDE_ENABLED/CODEX_ENABLED 플래그를 설정하세요.
  2. ClickHouse 수집 자격 증명을 /var/run/ccdash-clickhouse/CH_PASSWORD에, 내부 수신기 베어러 토큰을 /var/run/ccdash-ingest/token에 읽기 전용으로 마운트하세요. 컨테이너 사용자가 읽을 수 있어야 합니다. 이 내부 토큰을 클라이언트에 배포하지 마세요.
  3. 수신기 포트 4318과 상태 확인 포트 13133을 비공개로 유지하세요. 생성된 중앙 정책은 베어러 인증이 적용된 OTLP HTTP와 비공개 네이티브 ClickHouse 연결을 사용합니다. 경계를 넘는 연결에는 적절한 TLS 정책이 필요합니다.
  4. 필요한 파이프라인을 모두 활성화하세요. Claude 메트릭/로그/트레이스와 Codex 메트릭/로그/트레이스입니다. Codex 메트릭 파이프라인은 전용 테이블에 기록하고, 로그와 트레이스는 클라이언트 식별 정보를 유지하며 공유 테이블을 사용합니다.
  5. 장치 수집을 위해 대시보드의 OIDC 게이트, DynamoDB 장치 레지스트리, 런타임 IAM 권한, INGEST_ENABLED=1, INGEST_TOKEN_TABLE, INGEST_UPSTREAM_URL 및 INGEST_UPSTREAM_TOKEN_FILE을 구성하세요. 백엔드는 인증된 장치를 비공개 수신기로 전달합니다.

조직 관리 클라이언트의 경우 collector-config.yaml과 user-data.sh는 배포별 자격 증명 및 엔드포인트를 사용하는 별도의 로컬 Collector-to-ClickHouse 경로를 설명합니다. 구성을 그대로 복사해 두 경로를 결합하지 마세요.

EC2/Docker 호스트에서는 ClickHouse에 액세스할 수 있는 비공개 Docker 네트워크, 비밀 정보가 아닌 Collector 환경 파일, 보호된 보안 정보 파일 두 개를 준비하세요. infra/device_ingest.tf에서 다이제스트가 고정된 이미지를 선택하세요. 파일은 해당 이미지의 런타임 사용자가 읽을 수 있어야 합니다. 대시보드는 이 네트워크에서 중앙 수신기에 연결할 수 있으며 OTLP 포트나 상태 확인 포트를 호스트에 공개하지 않습니다.

: "${CCDASH_NETWORK:?Set the existing private Docker network}"
: "${CCDASH_COLLECTOR_IMAGE:?Set the pinned contrib image including its sha256 digest}"
: "${CCDASH_COLLECTOR_ENV_FILE:?Set the prepared nonsecret Collector environment file}"
: "${CCDASH_INGEST_SECRET_DIR:?Set the protected directory containing token}"
: "${CCDASH_INGEST_CH_SECRET_DIR:?Set the protected directory containing CH_PASSWORD}"
docker run -d --name ccdash-otel --restart unless-stopped \
  --network "$CCDASH_NETWORK" \
  --env-file "$CCDASH_COLLECTOR_ENV_FILE" \
  --mount "type=bind,src=$PWD/dashboard/collector/generated/central.yaml,dst=/etc/otelcol-contrib/config.yaml,readonly" \
  --mount "type=bind,src=$CCDASH_INGEST_SECRET_DIR,dst=/var/run/ccdash-ingest,readonly" \
  --mount "type=bind,src=$CCDASH_INGEST_CH_SECRET_DIR,dst=/var/run/ccdash-clickhouse,readonly" \
  "$CCDASH_COLLECTOR_IMAGE" --config=/etc/otelcol-contrib/config.yaml

이 네트워크에서 앱의 업스트림을 http://ccdash-otel:4318로 설정하고 동일한 내부 베어러 토큰을 INGEST_UPSTREAM_TOKEN_FILE에 마운트하세요. 이 토큰은 각 사용자의 장치 토큰과 다릅니다. 제공된 중앙 큐는 메모리 내에서 동작합니다. 운영 요구 사항에 맞춰 지속성/재시도와 손실 모니터링을 설계하세요.

중앙 수신기 및 장치 레지스트리 설정 · 중앙 Collector 구성 · 조직 관리 수집

4. 대시보드를 구성하고 시작

이미지를 시작하기 전에 데이터베이스 연결 및 인증 설정을 제공하세요. 다음은 비밀 정보가 없는 구성 템플릿입니다. 예시 엔드포인트, 발급자, 클라이언트 ID 및 그룹 이름을 배포 환경의 값으로 바꾸세요.

CH_URL=http://clickhouse.internal:8123
CH_DB=claude_code
CH_USER=otel_reader
CH_PASSWORD_FILE=/run/ccdash-secrets/CH_PASSWORD
CLAUDE_ENABLED=true
CODEX_ENABLED=true
AUTH_MODE=oidc
APP_PUBLIC_URL=https://dashboard.example.com
OIDC_ISSUER=https://issuer.example.com
OIDC_CLIENT_ID=YOUR_APP_CLIENT_ID
OIDC_ROLE_GROUPS={"viewer":["YOUR_VIEWER_GROUP"],"analyst":["YOUR_ANALYST_GROUP"],"admin":["YOUR_ADMIN_GROUP"]}
OIDC_CLIENT_SECRET_FILE=/run/ccdash-secrets/OIDC_CLIENT_SECRET
SESSION_SECRET_FILE=/run/ccdash-secrets/SESSION_SECRET

참조된 보안 정보 파일 세 개를 플랫폼의 보안 정보 관리 방식으로 제공하고 읽기 전용으로 마운트하세요. SESSION_SECRET은 base64url로 인코딩된 32바이트 난수 키여야 합니다. 파일 내용과 권한을 정확히 유지하세요. 런타임 이미지는 루트가 아닌 node 사용자로 실행됩니다. EC2에서는 컨테이너 구성에 동일한 절대 마운트 경로를 사용하세요. ECS/EKS에서는 해당하는 태스크/파드 보안 정보 전달 방식을 구현하세요. 공개 배포에서 안전하지 않은 개발용 인증을 활성화하지 마세요.

EC2/Docker 호스트에서 CCDASH_ENV_FILE과 CCDASH_SECRET_DIR을 준비한 다음, 별도로 구성한 HTTPS 리버스 프록시 뒤에서 앱을 실행합니다.

: "${CCDASH_RELEASE:?Set the built release tag}"
: "${CCDASH_ENV_FILE:?Set the prepared nonsecret environment file}"
: "${CCDASH_SECRET_DIR:?Set the runtime-readable protected secret directory}"
: "${CCDASH_NETWORK:?Set the existing private Docker network}"
docker run -d --name ccdash --restart unless-stopped \
  --network "$CCDASH_NETWORK" \
  --publish 127.0.0.1:8080:8080 \
  --env-file "$CCDASH_ENV_FILE" \
  --mount "type=bind,src=$CCDASH_SECRET_DIR,dst=/run/ccdash-secrets,readonly" \
  "ccdash:$CCDASH_RELEASE"

장치 수집을 활성화하려면 이전 단계의 내부 토큰 파일 마운트와 INGEST_* 설정도 앱의 런타임 구성에 추가하세요. 이 기본 앱 명령만으로 장치 레지스트리가 구성되거나 수집이 활성화되지는 않습니다.

OIDC 및 역할 구성 · 환경 변수 참고

EC2, ECS, EKS 또는 Lambda용 포팅 선택

옵션배포 형태저장소 지원 및 남은 작업
EC2 + Docker비공개 호스트나 네트워크에서 대시보드, Collector 및 영구 ClickHouse를 실행합니다. 내구성 있는 데이터베이스/큐 저장소와 HTTPS 진입점을 사용하세요.앱 이미지와 단일 노드 스키마가 제공됩니다. 호스트/서비스 수명 주기, 보안 정보, 데이터베이스 사용자, 네트워크 라우팅 및 백업은 직접 준비해야 합니다. 워크숍 user-data 스크립트는 클라이언트 수집을 구성하며 백엔드 전체를 구성하지 않습니다.
ECS / Fargate앱과 Collector 이미지를 ECR에 게시하고 별도 서비스 또는 적절한 사이드카로 실행합니다. 비공개 네트워킹과 별도로 관리되는 영구 ClickHouse 설치를 사용하세요.ECS 태스크/서비스 템플릿은 제공되지 않습니다. 태스크/실행 역할, 보안 정보 전달, CPU/메모리, 이미지 아키텍처, 상태 확인 및 서비스 연결을 정의하세요. 데이터베이스나 내구성 있는 큐에 임시 태스크 파일 시스템을 사용하지 마세요.
EKS기존 클러스터, ClickHouse/Keeper 오퍼레이터 및 영구 볼륨을 사용하고 저장소의 Terraform으로 앱과 선택적 중앙 수신기를 배포합니다.infra/는 기존 클러스터/VPC를 재사용합니다. 오퍼레이터, Karpenter, CSI/스토리지, DNS/인증서, IAM 및 보안 정보를 준비한 다음 계획/적용하고, 스키마 초기화를 확인하고, 검토된 이미지를 게시해 롤아웃하세요. 모든 사전 요구 사항이 자동으로 생성되지는 않습니다.
LambdaHTTP 애플리케이션을 Lambda 호환 런타임/어댑터로 포팅합니다. ClickHouse와 수집 Collector는 영구 외부 서비스로 유지하세요.현재 Docker 이미지는 Express를 시작하며 Lambda 핸들러/런타임 통합이 없습니다. 바로 사용할 수 있는 Lambda 배포 구성은 제공되지 않습니다. 포팅 후 인증 쿠키, 스트리밍/채팅, 시간 제한, 네트워킹 및 장치 수집을 검증하세요. Lambda를 선택하는 것만으로 이 스택이 설치되지는 않습니다.

공식 플랫폼 참고 자료: EC2 · ECS/Fargate 태스크 정의 · EKS 애플리케이션 배포 · Lambda 이미지/런타임 요구 사항.

5. 클라이언트 로그, 메트릭 및 트레이스 연결

백엔드가 동작하면 각 클라이언트의 로컬 Collector와 내보내기 대상 주소를 구성하세요. 장치 경로의 경우 analyst/admin이 배포된 대시보드에서 장치를 등록할 수 있습니다. 다운로드할 수 없다면 소스 설치 프로그램을 직접 사용하세요. 그래도 설치된 백엔드와 발급된 장치 토큰이 필요합니다.

: "${CCDASH_INGEST_ENDPOINT:?Set the deployed HTTPS dashboard URL ending in /api/ingest}"
: "${CCDASH_USER_ID:?Set the intended telemetry attribution ID}"
python3 dashboard/collector/install.py install \
  --endpoint "$CCDASH_INGEST_ENDPOINT" --user-id "$CCDASH_USER_ID"

설치 프로그램은 macOS/Linux에서 Python 3.9 이상이 필요하며 토큰을 비공개로 입력하라는 메시지를 표시합니다. Linux에서는 로그아웃/재부팅 후에도 서비스가 유지되도록 sudo loginctl enable-linger "$USER"를 실행한 다음 일반 사용자로 설치하세요. Collector 바이너리를 다운로드하고 검증합니다. 이 명령은 대시보드, 데이터베이스 또는 중앙 수신기를 준비하지 않습니다. 장치 소유자가 자동으로 텔레메트리의 사용자 식별 정보가 되는 것은 아닙니다.

  • Claude Code: 텔레메트리와 향상된 텔레메트리를 활성화하고 OTEL_TRACES_EXPORTER=otlp를 설정한 뒤 포트 4317의 로컬 OTLP gRPC 대상으로 보냅니다.
  • Codex: 별도의 [otel] exporter, metrics_exporter 및 trace_exporter 항목을 사용하고, 포트 4318의 로컬 OTLP HTTP 대상과 log_user_prompt=false를 설정합니다.

두 클라이언트를 다시 시작하고 새 작업을 생성한 뒤 사용자 → 추세 버킷 → 작업 → Task Trace를 따라가세요. 이전 활동은 트레이스로 소급 처리되지 않습니다. Codex 진단 스팬은 Analytics의 Trace 탭에서 확인하세요.

기존 장치 및 데이터베이스

장치 마이그레이션 중에는 비공개 클라이언트 백업과 내보내기 큐를 보존하세요. 알 수 없는 서비스를 중지하는 대신 지원되는 macOS/Linux 마이그레이션 절차를 따르세요. 데이터베이스 업그레이드는 클라이언트 설치 및 애플리케이션 롤아웃과 별도로 스키마 런북을 따릅니다.

6. 모든 경계 검증

  1. /healthz와 ClickHouse 기반 /readyz를 확인한 다음 인증하고 설치/스키마 진단을 살펴보세요.
  2. 예상 테이블, 마이그레이션 원장, 뷰, 데이터베이스 권한 및 Collector 쓰기 성공을 확인하세요. 스키마가 있다는 사실만으로 과거 데이터가 준비된 것은 아닙니다.
  3. 새 클라이언트 작업을 보내고 의도한 사용자 식별 정보로 저장된 로그, 메트릭 및 트레이스를 확인하세요. Collector 프로세스 실행이나 장치 수신 확인만으로 데이터가 영구 저장되었다고 볼 수 없습니다.
  4. 선택한 사용자의 사용량과 Task Trace를 확인하세요. Codex 트레이스/메트릭 관측값은 진단 정보이므로 비용 합계를 추가해서는 안 됩니다.

조직이 준비한 워크숍

준비된 워크숍은 자체 클라이언트 및 Collector 수명 주기를 가집니다. 참가자는 구성된 환경을 사용하며 두 번째 백엔드를 배포하거나 준비된 서비스 위에 Collector를 추가로 설치하지 않습니다. 주최자는 user-data.sh를 사용하기 전에 스키마, 보안 정보 대상 및 부트스트랩 자산을 제공해야 합니다.
