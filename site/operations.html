Connect organization SSO

Set AUTH_MODE=oidc for a confidential OIDC client with discovery/JWKS, signed ID tokens, authorization code and PKCE S256. Register the exact callback https://dashboard.example.com/auth/callback.

A shared Cognito user pool can serve multiple projects through separate app clients, callbacks, secrets and role mappings. Application-specific group assignment belongs in identity administration. Customer emails, domains and pool IDs are configuration, not general application rules.

SettingPurpose
APP_PUBLIC_URLExact HTTPS origin, without a path, query or fragment.
OIDC_ISSUER, OIDC_CLIENT_IDExact issuer identifier and the dedicated application client.
OIDC_CLIENT_SECRET, SESSION_SECRETProvision through protected secret references. Replicas must share the session key and identity configuration.
OIDC_GROUPS_CLAIMTop-level signed group claim: for Cognito, cognito:groups; otherwise the provider's configured claim.
OIDC_SCOPESDefault openid profile. Add only scopes needed by the configured provider, including refresh issuance requirements.
OIDC_ROLE_GROUPSJSON mapping from viewer, analyst and admin to explicit group arrays.
{
  "viewer": ["YOUR_VIEWER_GROUP"],
  "analyst": ["YOUR_EDITOR_GROUP"],
  "admin": ["YOUR_ADMIN_GROUP"]
}

The UI's editor role maps to analyst; editor is not a configuration role key. Unmapped groups cannot log in. The highest mapped role wins.

RolePermissions
viewerRead installation-wide telemetry; no Collector management or chat.
analyst / editorRead telemetry, use enabled chat, download installers and manage owned devices.
adminAnalyst permissions plus installation diagnostics.

Okta and Keycloak can supply this OIDC contract with the appropriate scopes and signed group claims. Verify the actual customer provider; generic support is not a completed provider acceptance test. Login does not provide per-user data isolation.

Provider setup and SSO operations

Keep login for up to 30 days

Persistent login is optional and disabled by default. A one-hour authorization ceiling with a fixed 30-day login limit can be configured as:

SESSION_MAX_AGE_SECONDS=3600
SESSION_REFRESH_MAX_AGE_SECONDS=2592000

The normal short-session default is 900 seconds; permitted values are 300–3600. Refresh lifetime is either 0 (disabled) or 3600–2592000 seconds. Short sessions are also bounded by provider token expiry, so one hour is a ceiling rather than a guaranteed renewal interval.

Renewal is request-driven near or after short-session expiry, not a background hourly timer. The 30-day deadline starts at initial login and does not slide forward. The provider can end it earlier.

  • Refresh mode requires a reusable non-rotating refresh token, a fresh signed ID token with current groups, and exchange/revocation using client_secret_basic.
  • Rotation-only providers are unsupported in this mode. A rotated refresh response requires a new login.
  • Use encrypted Secure/HttpOnly cookies. Raw identity tokens are not returned by the session API.
  • Logout clears local cookies and attempts refresh revocation. It does not end the provider's SSO session, instantly revoke copied short-lived cookies, or revoke device tokens.

Deploy a reviewed application revision

  1. Use a clean, reviewed build context and record its commit. Follow the deployment runbook's preflight checks.
  2. Confirm AWS identity, target cluster, existing Terraform inputs, migration state and a usable rollback image.
  3. Build for the target architecture and publish an immutable image tag/digest. The provided EKS deployment targets arm64.
  4. Review the complete infrastructure plan where needed. Existing installations use compatibility verification and explicit upgrades, not automatic bootstrap retries.
  5. Roll out, check readiness and actual image digests, then verify login, API behavior, ingestion freshness and representative data.

Use /healthz for liveness and /readyz for readiness. Source declarations, passing builds and a healthy process do not establish a working identity provider, fresh telemetry or applied migrations.
