Claude Code + Codex · インストール

サービス全体をビルドしてデプロイする

Gitソースから始めます。コーディングクライアントを接続する前に、ダッシュボード、ClickHouseとそのスキーマ、OTelの収集経路をデプロイします。

更新日: 2026年11月10日 · ソースに基づく手順です。選択したリリースと対象環境を確認してください。

クローンとビルド · データベーススキーマ · OTelバックエンド · ホスティングの選択肢 · クライアントのトレース

インストールが必要なもの

このガイドでは、公開済みのアプリケーション用 .tar.gz に依存しません。リポジトリをクローンしてDockerイメージをビルドします。オプションのデバイス用パッケージは、インストール済みのダッシュボードから生成されます。バックエンドをインストールするものではありません。

コンポーネント用途とソース
ダッシュボードアプリケーションdashboard/Dockerfile はReactとExpressを1つのイメージにビルドし、ポート8080でUIとAPIを提供します。ClickHouseやOTel Collectorは実行しません。
ClickHouseとスキーマ永続データベース、テレメトリテーブル、マテリアライズドビュー、移行台帳です。デプロイに応じて、単一ノード用またはレプリケーション用のスキーマを選択します。
OTel Collector別途実行するCollectorがログ、メトリクス、トレースを受信し、リポジトリのフィルターと変換を適用して、準備済みのテーブルに書き込みます。
認証とシークレットOIDCまたは設定済みのBasic認証、HTTPSアクセス、非公開のデータベース接続、読み取り用・取り込み用・管理用に分離した認証情報、保護されたシークレットのマウントを用意します。
クライアントの収集Claude Code/Codexエクスポーターと、ローカルCollectorまたは組織管理の収集経路を用意します。バックエンドのデプロイによって、ユーザーのクライアント設定が変わることはありません。

まずGitとbuildx対応のDockerをインストールします。EKSの場合は、組織向けデプロイの前提条件に記載された既存クラスターの依存関係、Terraform、AWS CLI、kubectlも準備してください。

1. リリースをクローンしてイメージをビルドする

CCDASH_RELEASE には、実際に公開されている vX.Y.Z リリースタグを設定します。実行環境に合わせてプラットフォームを選択してください。提供されているEKSデプロイでは linux/arm64 を使用します。

: "${CCDASH_RELEASE:?Set a published vX.Y.Z release tag}"
CCDASH_PLATFORM=linux/arm64
git clone https://github.com/Atom-oh/claude-code-usage-dashboard.git
cd claude-code-usage-dashboard
git checkout --detach "$CCDASH_RELEASE"
CCDASH_REVISION=$(git rev-parse HEAD)
docker build --platform "$CCDASH_PLATFORM" \
  --build-arg APP_REVISION="$CCDASH_REVISION" \
  --tag "ccdash:$CCDASH_RELEASE" dashboard

ビルドコンテキストはリポジトリのルートではなく dashboard/ です。x86環境では linux/amd64 を選び、そのデプロイを個別に適格性確認してください。異なるアーキテクチャでビルドする場合は、クロスプラットフォームビルダーの設定が必要です。

本番環境では、レビュー済みのビルド、検査、レジストリへの公開、ロールアウト手順に従ってください。リリース、ソースリビジョン、イメージダイジェストを保持します。ローカルビルドが成功しただけで、デプロイ済みと見なさないでください。

2. 取り込みを始める前にClickHouseを準備する

まず永続的なClickHouseストレージとバックアップ／復旧を用意します。読み取り専用のダッシュボードアカウント、必要なエクスポーター権限を持つ取り込みアカウント、管理用の移行アカウントを作成してください。スキーマファイルは本番ユーザーを作成しません。

提供されているアカウントポリシーでは、otel_reader に claude_code.* のSELECT権限を付与します。otel_ingest アカウントには、claude_code.* へのINSERT権限と、マテリアライズドビューのソース読み取り用に claude_code.otel_metrics_sum のSELECT権限が必要です。INSERTだけでは取り込みに失敗することがあります。アカウントの接続元ネットワークを制限し、リポジトリのClickHouseアカウントポリシーを参考に、保護された認証情報を設定してください。

デプロイスキーマのパス
新規の単一ノード／ローカル評価clickhouse-schema.sql: 非レプリケーションテーブル、ビュー、ロールアップ、現在の移行ガードを含みます。Claudeテレメトリと、Codex専用のメトリクス／コスト／診断テーブルも含まれます。
新規のレプリケーション構成EKSinfra/files/clickhouse-schema-replicated.sql と、infra/schema.tf 内の生成済みコントラクトおよびschema-init Jobを使用します。宣言済みのクラスター／Keeperトポロジーと想定レプリカ数が必要です。
既存のインストールテーブル、台帳、過去データを確認してください。各ランブックに従い、必要な番号付き移行だけを適用します。アップグレードとしてブートストラップを再実行しないでください。

EC2/Dockerでは、次のものを準備してください。

  • 専用のブリッジネットワークと永続データボリューム。
  • 読み取り用／取り込み用／管理用アカウント、制限されたネットワーク、匿名のデフォルトアクセスなしを設定した保護済みの users.d XMLと、管理者クライアント設定。
  • 選択したリリース向けに適格性を確認して固定したClickHouseイメージ。ローカルのCompose設定は出発点となる参考例です。

CLICKHOUSE_SKIP_USER_SETUP=1 は準備済みのアカウント設定を保持します。まず認証とネットワーク制限を検証してください。次のコマンドはデータベースのポートを公開せずに起動します。

: "${CCDASH_NETWORK:?Set the prepared private Docker network}"
: "${CCDASH_CH_CONTAINER:?Set the ClickHouse container name}"
: "${CCDASH_CH_IMAGE:?Set the reviewed ClickHouse image including its sha256 digest}"
: "${CCDASH_CH_DATA_VOLUME:?Set the prepared persistent data volume}"
: "${CCDASH_CH_USERS_DIR:?Set the protected users.d configuration directory}"
: "${CCDASH_CH_ADMIN_CONFIG:?Set the protected admin client configuration file}"
docker run -d --name "$CCDASH_CH_CONTAINER" --restart unless-stopped \
  --network "$CCDASH_NETWORK" --network-alias clickhouse.internal \
  --env CLICKHOUSE_SKIP_USER_SETUP=1 \
  --mount "type=volume,src=$CCDASH_CH_DATA_VOLUME,dst=/var/lib/clickhouse" \
  --mount "type=bind,src=$CCDASH_CH_USERS_DIR,dst=/etc/clickhouse-server/users.d,readonly" \
  --mount "type=bind,src=$CCDASH_CH_ADMIN_CONFIG,dst=/run/ccdash-admin/client.xml,readonly" \
  "$CCDASH_CH_IMAGE"

ClickHouseの起動を待ち、マウントした管理者クライアント設定で認証します。下記のスキーマ用コマンドでは、コンテナ内のパスは /run/ccdash-admin/client.xml です。このネットワーク上のアプリとCollectorでは、データベースホストに clickhouse.internal を使用します。イメージとマウントした設定は、実行時のアーキテクチャおよびファイル読み取り権限に適合している必要があります。

新規で空の非レプリケーションデータベースの場合、CCDASH_CH_CONTAINER に実行中のClickHouseコンテナを、CCDASH_CH_CLIENT_CONFIG にそのコンテナ内の保護された管理者クライアント設定のパスを設定します。

: "${CCDASH_CH_CONTAINER:?Set the prepared ClickHouse container name}"
: "${CCDASH_CH_CLIENT_CONFIG:?Set the mounted admin client configuration path}"
docker exec -i "$CCDASH_CH_CONTAINER" \
  clickhouse-client --config-file "$CCDASH_CH_CLIENT_CONFIG" \
  --multiquery < clickhouse-schema.sql

docker exec "$CCDASH_CH_CONTAINER" clickhouse-client \
  --config-file "$CCDASH_CH_CLIENT_CONFIG" \
  --query "SELECT name FROM system.tables WHERE database='claude_code' ORDER BY name"

otel_logs、otel_traces、Claudeのメトリクステーブル、Codexの4つのメトリクステーブル、ビュー、schema_migrations を確認します。Collectorは create_schema: false を使用するため、不足テーブルを補完できません。移行003では、ロールアップの切り替えをステートメント単位で行う必要があります。型付き読み取りを有効にするには、テーブルの存在だけでなく、履歴データとライブデータの両方が利用可能であることも検証してください。

既存の dashboard/docker-compose.yml は、新しいローカルClickHouseボリュームと合成シードデータを初期化します。開発用認証を使い、OTel Collectorサービスは含みません。評価を始めるための構成であり、本番向けの完全なインストールではありません。既存のボリュームは再初期化されません。

3. OTelバックエンドをインストールする

ClickHouseエクスポーターと必要なプロセッサーを含むCollectorディストリビューションを実行します。オプションのデバイストークン経路では、dashboard/collector/generated/central.yaml がリポジトリの非公開な中央レシーバーポリシーです。infra/device_ingest.tf にあるレビュー済みのContribイメージをダイジェストで固定して使用してください。

  1. 中央YAMLをCollector設定としてマウントします。CH_HOST、CH_PORT（ネイティブポート）、CH_DB=claude_code、CH_USER、および対応する CLAUDE_ENABLED/CODEX_ENABLED フラグを設定します。
  2. ClickHouseの取り込み用認証情報を /var/run/ccdash-clickhouse/CH_PASSWORD に、内部レシーバーのBearerトークンを /var/run/ccdash-ingest/token に読み取り専用でマウントします。コンテナの実行ユーザーが読み取れることを確認してください。この内部トークンをクライアントに配布しないでください。
  3. レシーバーのポート4318とヘルスチェックのポート13133は非公開にします。生成済みの中央ポリシーは、Bearer認証付きOTLP HTTPと非公開のClickHouseネイティブ接続を使用します。ネットワーク境界を越える接続には、適切なTLSポリシーが必要です。
  4. 必要なすべてのパイプライン、すなわちClaudeのメトリクス／ログ／トレースとCodexのメトリクス／ログ／トレースを有効にします。Codexのメトリクスパイプラインは専用テーブルに書き込みます。ログとトレースは、クライアント識別情報を保持したまま共有テーブルを使用します。
  5. デバイス取り込みでは、ダッシュボードのOIDCゲート、DynamoDBデバイスレジストリ、実行時のIAM権限、INGEST_ENABLED=1、INGEST_TOKEN_TABLE、INGEST_UPSTREAM_URL、INGEST_UPSTREAM_TOKEN_FILE を設定します。バックエンドは認証済みデバイスからのデータを非公開レシーバーに転送します。

組織管理のクライアントでは、collector-config.yaml と user-data.sh が、ローカルCollectorからClickHouseへの別の経路を定義します。デプロイ固有の認証情報とエンドポイントを使用します。2つの経路を、設定を変更せずにコピーして組み合わせないでください。

EC2/Dockerホストでは、ClickHouseに接続できる非公開Dockerネットワーク、シークレットを含まないCollector環境ファイル、2つの保護されたシークレットファイルを準備します。infra/device_ingest.tf からダイジェストで固定されたイメージを選びます。ファイルは、そのイメージの実行ユーザーが読み取れる必要があります。中央レシーバーはこのネットワーク上でダッシュボードから到達できます。OTLPポートやヘルスチェックポートはホストに公開しません。

: "${CCDASH_NETWORK:?Set the existing private Docker network}"
: "${CCDASH_COLLECTOR_IMAGE:?Set the pinned contrib image including its sha256 digest}"
: "${CCDASH_COLLECTOR_ENV_FILE:?Set the prepared nonsecret Collector environment file}"
: "${CCDASH_INGEST_SECRET_DIR:?Set the protected directory containing token}"
: "${CCDASH_INGEST_CH_SECRET_DIR:?Set the protected directory containing CH_PASSWORD}"
docker run -d --name ccdash-otel --restart unless-stopped \
  --network "$CCDASH_NETWORK" \
  --env-file "$CCDASH_COLLECTOR_ENV_FILE" \
  --mount "type=bind,src=$PWD/dashboard/collector/generated/central.yaml,dst=/etc/otelcol-contrib/config.yaml,readonly" \
  --mount "type=bind,src=$CCDASH_INGEST_SECRET_DIR,dst=/var/run/ccdash-ingest,readonly" \
  --mount "type=bind,src=$CCDASH_INGEST_CH_SECRET_DIR,dst=/var/run/ccdash-clickhouse,readonly" \
  "$CCDASH_COLLECTOR_IMAGE" --config=/etc/otelcol-contrib/config.yaml

このネットワークでは、アプリの上流エンドポイントを http://ccdash-otel:4318 に設定し、同じ内部Bearerトークンを INGEST_UPSTREAM_TOKEN_FILE にマウントします。このトークンは各ユーザーのデバイストークンとは異なります。提供されている中央キューはメモリ上にあります。運用要件に応じて、永続化／再試行とデータ損失の監視を設計してください。

4. ダッシュボードを設定して起動する

イメージの起動前に、データベース接続と認証設定を指定します。以下はシークレットを含まない設定テンプレートです。例示用のエンドポイント、発行者、クライアントID、グループ名をデプロイ環境の値に置き換えてください。

CH_URL=http://clickhouse.internal:8123
CH_DB=claude_code
CH_USER=otel_reader
CH_PASSWORD_FILE=/run/ccdash-secrets/CH_PASSWORD
CLAUDE_ENABLED=true
CODEX_ENABLED=true
AUTH_MODE=oidc
APP_PUBLIC_URL=https://dashboard.example.com
OIDC_ISSUER=https://issuer.example.com
OIDC_CLIENT_ID=YOUR_APP_CLIENT_ID
OIDC_ROLE_GROUPS={"viewer":["YOUR_VIEWER_GROUP"],"analyst":["YOUR_ANALYST_GROUP"],"admin":["YOUR_ADMIN_GROUP"]}
OIDC_CLIENT_SECRET_FILE=/run/ccdash-secrets/OIDC_CLIENT_SECRET
SESSION_SECRET_FILE=/run/ccdash-secrets/SESSION_SECRET

ダッシュボードを起動する前に、次のシークレット要件を満たしてください。

  • 参照されている3つのファイルをプラットフォームのシークレット管理機能で用意し、読み取り専用でマウントします。
  • SESSION_SECRET にはbase64url形式でエンコードした32バイトのランダムキーを使用します。ファイルの内容と読み取り権限を正確に保ってください。実行時のイメージは非rootの node ユーザーを使用します。
  • EC2ではコンテナ設定に同じ絶対マウントパスを指定します。ECS/EKSでは対応するタスク／Podへのシークレット配信を実装します。

公開デプロイで安全でない開発用認証を有効にしないでください。

EC2/Dockerホストで CCDASH_ENV_FILE と CCDASH_SECRET_DIR を準備した後、別途設定したHTTPSリバースプロキシの背後でアプリを実行します。

: "${CCDASH_RELEASE:?Set the built release tag}"
: "${CCDASH_ENV_FILE:?Set the prepared nonsecret environment file}"
: "${CCDASH_SECRET_DIR:?Set the runtime-readable protected secret directory}"
: "${CCDASH_NETWORK:?Set the existing private Docker network}"
docker run -d --name ccdash --restart unless-stopped \
  --network "$CCDASH_NETWORK" \
  --publish 127.0.0.1:8080:8080 \
  --env-file "$CCDASH_ENV_FILE" \
  --mount "type=bind,src=$CCDASH_SECRET_DIR,dst=/run/ccdash-secrets,readonly" \
  "ccdash:$CCDASH_RELEASE"

デバイス取り込みを有効にするには、前の手順にある内部トークンファイルのマウントと INGEST_* 設定も、アプリの実行時設定に追加します。この基本的なアプリ起動コマンドだけでは、デバイスレジストリの設定も取り込みの有効化も行われません。

5. クライアントのログ、メトリクス、トレースを接続する

バックエンドが動作したら、各クライアントのローカルCollectorとエクスポーターの送信先を設定します。デバイス経路では、アナリストまたは管理者がデプロイ済みダッシュボードにデバイスを登録できます。ダウンロードできない場合は、ソースインストーラーを直接使用してください。その場合も、インストール済みのバックエンドと発行済みのデバイストークンが必要です。

: "${CCDASH_INGEST_ENDPOINT:?Set the deployed HTTPS dashboard URL ending in /api/ingest}"
: "${CCDASH_USER_ID:?Set the intended telemetry attribution ID}"
python3 dashboard/collector/install.py install \
  --endpoint "$CCDASH_INGEST_ENDPOINT" --user-id "$CCDASH_USER_ID"

インストーラーはmacOS/Linux上のPython 3.9以降を必要とし、トークンは非公開で入力するよう求めます。Linuxでは、ログアウト／再起動後もサービスを維持するために sudo loginctl enable-linger "$USER" を実行してから、通常ユーザーとしてインストールします。Collectorバイナリをダウンロードして検証します。このコマンドはダッシュボード、データベース、中央レシーバーを準備しません。デバイスの所有者が、出力されるテレメトリのIDとして自動的に使われるわけではありません。

  • Claude Code: CLAUDE_CODE_ENABLE_TELEMETRY=1 と CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1 を設定し、OTEL_TRACES_EXPORTER=otlp とポート4317のローカルOTLP gRPC送信先を指定します。
  • Codex: 個別に [otel] の exporter、metrics_exporter、trace_exporter を設定します。ポート4318のローカルOTLP HTTP送信先と、log_user_prompt=false を指定してください。

両方のクライアントを再起動して新しい作業を生成し、ユーザー → トレンドバケット → タスク → Task Traceをたどります。以前のアクティビティがトレースに遡及して取り込まれることはありません。Codexの診断spanを確認するには、AnalyticsのTraceタブを開きます。

既存のデバイスとデータベース

デバイス移行時には、クライアントの非公開バックアップとエクスポーターのキューを保持してください。正体不明のサービスを停止せず、サポートされているmacOS/Linuxの移行手順に従います。データベースのアップグレードは、クライアントのインストールやアプリケーションのロールアウトとは別に、スキーマのランブックに従って行います。

ソースインストーラーと移行ガイド

6. すべての境界を検証する

  1. /healthz とClickHouseに依存する /readyz を確認してから認証し、インストール／スキーマ診断を確認します。
  2. 想定したテーブル、移行台帳、ビュー、データベース権限、Collectorの書き込み成功を確認します。スキーマが存在するだけでは、過去データが利用可能とは限りません。
  3. 新しいクライアント作業を送信し、意図したIDでログ、メトリクス、トレースが保存されていることを確認します。Collectorプロセスの稼働やデバイスの受信応答だけでは、データの永続化は証明されません。
  4. 選択したユーザーの利用状況とTask Traceを確認します。Codexのトレース／メトリクス観測は診断用であり、コスト合計に重ねて加算してはいけません。
