組織のSSOを接続する

AUTH_MODE=oidcを設定すると、ディスカバリー/JWKS、署名済みIDトークン、認可コード、PKCE S256を使用する機密クライアント向けOIDCを有効にできます。コールバックには正確にhttps://dashboard.example.com/auth/callbackを登録してください。

共有のCognitoユーザープールは、アプリクライアント、コールバック、シークレット、ロールマッピングを個別に設定して、複数のプロジェクトで使用できます。アプリケーション固有のグループ割り当ては、ID管理側で行います。顧客のメールアドレス、ドメイン、ユーザープールIDは設定値であり、アプリケーション全般のルールではありません。

設定項目用途
APP_PUBLIC_URLパス、クエリ、フラグメントを含まない、正確なHTTPSオリジン。
OIDC_ISSUER, OIDC_CLIENT_ID正確なIssuer識別子と、専用のアプリケーションクライアント。
OIDC_CLIENT_SECRET, SESSION_SECRET保護されたシークレット参照を通じて設定します。レプリカ間でセッションキーとID設定を共有する必要があります。
OIDC_GROUPS_CLAIM署名済みのトップレベルグループクレーム。Cognitoではcognito:groups、それ以外ではプロバイダーで設定したクレームを指定します。
OIDC_SCOPES既定値はopenid profileです。更新トークンの発行要件を含め、設定済みプロバイダーに必要なスコープだけを追加します。
OIDC_ROLE_GROUPSviewer、analyst、adminを明示的なグループ配列に対応付けるJSONマッピング。
{
  "viewer": ["YOUR_VIEWER_GROUP"],
  "analyst": ["YOUR_EDITOR_GROUP"],
  "admin": ["YOUR_ADMIN_GROUP"]
}

UIのeditorロールはanalystに対応します。editorは設定上のロールキーではありません。マッピングされていないグループはログインできません。複数のロールに該当する場合は、最も権限の高いロールが適用されます。

ロール権限
viewerインストール全体のテレメトリを閲覧できます。Collectorの管理とチャットは利用できません。
analyst / editorテレメトリの閲覧、有効なチャットの利用、インストーラーのダウンロード、所有デバイスの管理ができます。
adminanalystの権限に加え、インストール環境の診断ができます。

OktaとKeycloakは、適切なスコープと署名済みグループクレームを使って、このOIDC仕様を提供できます。実際の顧客プロバイダーで確認してください。一般的な対応をうたっていても、プロバイダーの受け入れテストが完了したことを意味しません。ログインしてもユーザーごとのデータ分離は行われません。

プロバイダーの設定とSSOの運用

ログイン状態を最大30日間維持する

ログイン状態の永続化は任意で、既定では無効です。認可期間の上限を1時間、ログイン期間の固定上限を30日にするには、次のように設定します。

SESSION_MAX_AGE_SECONDS=3600
SESSION_REFRESH_MAX_AGE_SECONDS=2592000

通常の短期セッションの既定値は900秒で、設定可能な値は300～3600秒です。更新トークンの有効期間は、0（無効）または3600～2592000秒です。短期セッションはプロバイダーのトークン有効期限によっても制限されるため、1時間は上限であり、更新間隔が保証されるわけではありません。

更新はバックグラウンドで毎時行われるのではなく、短期セッションの期限が近づいたとき、または期限切れ後のリクエストを契機に行われます。30日の期限は初回ログイン時に始まり、延長されません。プロバイダーによっては、それより早く終了することがあります。

  • 更新モードには、再利用可能でローテーションされない更新トークン、現在のグループを含む新しい署名済みIDトークン、client_secret_basicによるトークン交換と失効処理が必要です。
  • このモードでは、ローテーションのみをサポートするプロバイダーは利用できません。更新トークンがローテーションされた場合は、再ログインが必要です。
  • 暗号化されたSecure/HttpOnly Cookieを使用してください。セッションAPIは生のIDトークンを返しません。
  • ログアウト時はローカルCookieを消去し、更新トークンの失効を試みます。プロバイダーのSSOセッションは終了せず、コピー済みの短期Cookieを即座に失効させることも、デバイストークンを失効させることもありません。

更新セッションの設計と制限

レビュー済みのアプリケーションリビジョンをデプロイする

  1. リリースPRをマージし、クリーンなビルドコンテキストから不変のvX.Y.Zタグをデプロイします。コミットを記録し、デプロイ手順書の事前確認に従ってください。
  2. AWSのID、対象クラスター、既存のTerraform入力値、マイグレーションの状態、利用可能なロールバック用イメージを確認します。
  3. 対象アーキテクチャ向けにビルドし、不変のイメージタグ/ダイジェストを公開します。提供されているEKSデプロイの対象はarm64です。
  4. 必要に応じて、インフラストラクチャ計画全体をレビューします。既存のインストール環境では、互換性を確認したうえで明示的にアップグレードします。自動ブートストラップの再試行は行いません。
  5. ロールアウトし、準備状態と実際のイメージダイジェストを確認してから、ログイン、APIの動作、データ取り込みの鮮度、代表的なデータを検証します。

稼働状態には/healthz、準備状態には/readyzを使用します。ソース上の宣言、成功したビルド、正常なプロセスだけでは、IDプロバイダーの動作、テレメトリの鮮度、マイグレーションの適用は確認できません。

問題が起きている境界から調べる

症状最初に確認する項目
ログインに失敗する、または早期に終了するオリジン/コールバック/Issuerの正確性、署名済みグループのマッピング、プロバイダーの有効期限と更新仕様を確認します。トークンの値を出力しないでください。
Collectorのポートが使用中選択したリリースのソースインストーラーを使用します。macOSのサポート対象の移行手順か、既存サービスの所有者による手動手順に従ってください。
ユーザーが特定できない、または分割されている意図した--user-id、出力されたID、ダッシュボードのフィルターを確認します。デバイスのSSO所有者がテレメトリの属性に自動で反映されるわけではありません。
トークンは発行されたがテレメトリがないコーディングクライアントを再起動して作業を実行し、ローカルサービス/エクスポーターのエラーとデバイスでの受信を確認した後、保存データを確認します。
Codexの詳細がダッシュで表示される完了データのコホートと、ウィンドウ全体の完全性をそれぞれ確認します。分母、価格、コンポーネントが欠けている場合に、ゼロとして扱ってはいけません。
コスト詳細の表示が遅いクエリの受け入れ状況、フィルター、有効な解像度を確認します。コスト/作業量プロファイルを使用し、容量を変更する前に対象ワークロードを測定してください。

プラットフォーム別の運用要件

どのホスティング方式でも、永続的なClickHouseスキーマと、正常に動作するOTelパイプラインが必要です。ECSとEC2では、サービス、シークレット、ストレージの設定を別途作成する必要があります。提供されているTerraformの対象は既存のEKS環境です。Lambdaには、アプリケーションランタイムへの適応と、外部データベース/Collectorサービスが必要です。

デプロイ方法とサポート範囲 · スキーマの初期化 · Collectorの設定

ドキュメントのデプロイ

このドキュメントはsite/内の静的HTMLです。Pagesワークフローは、mainへの変更がマージされると、このディレクトリをアップロードします。ドキュメントのみのリリースでは、バンドラーによるビルドも、アプリケーション/EKSのロールアウトもありません。

完全な手順については、ソースにリンクされた運用手順書を参照してください。ウェブサイトにはサポート対象の動作を要約していますが、特定の顧客環境の設定を保証するものではありません。

Trace の経路を確認する

新しいインタラクションと、そのインタラクションに期待されるテレメトリー ID、クライアント、時間バケットから確認を始めます。利用状況の合計と Trace の利用可否は異なるシグナルに基づきます。ログのエクスポートが成功しても、トレースが配信されたことにはなりません。

  1. 現在のデバイスパッケージ、または管理者が管理する設定でトレースのエクスポートが有効になっていることを確認し、コーディングクライアントを再起動します。クライアント設定リファレンスを参照してください。
  2. ローカル Collector のサービスとトレースエクスポーターで、配信エラーがないか確認します。続いて、認証済み取り込み、中央トレースパイプライン、保存済みの otel_traces レコードを確認します。デバイスでの受信確認とプロセスの正常性が確認できるのは、それぞれの段階のみです。
  3. ユーザー詳細で、タスクの開始時刻を含む時間範囲を選択します。タスクリストは有効範囲に追従します。ドラッグして範囲を絞り込むか、1つのバケットをクリックします。期間全体に戻すには、全期間へのリセットを使います。想定される ID とフィルターを確認してください。サポート対象のトレースタスクは90日間保持されます。
  4. Codex の診断情報は、完全な insights プロファイルを使って Analytics の Trace タブで確認します。コスト／作業量、ツール、パフォーマンスの各プロファイルでは、トレースのクエリは実行されません。
症状確認事項
利用状況はあるがタスクがないトレース設定、再起動時刻、エクスポートされた ID、タスクの開始時刻の範囲、保持期間を確認します。過去の利用状況はトレースにバックフィルされません。
Codex の完了記録がタスクに紐づかないトレースされたターンには会話 ID と一意のターン ID が必要です。条件を満たすターンがない完了記録は未関連付けのままです。サンプリングスパンを伴わない関連付け済みの完了記録は、コスト帯に表示されない場合があります。
Codex のサブエージェント数が利用できない現在のタスクビューにはメインレーンのみがあり、無関係なスパンからサブエージェント数を推定しません。
詳細が大きい場合に合計が表示されないtruncated と span_total を確認します。タスク詳細の上限は5,000スパンです。別の診断プレビューでは、合計50トレース、トレースあたり最大200スパンを使用します。
モデルフィルターを適用すると Codex Trace が表示されないそのフィルターに一致するのは、モデル属性を持つスパンのみです。他の診断スパンを確認するには、フィルターを解除します。
単価グラフの線が破線になっているその間隔には、マッチしたセッションについて計算可能な値がありません。破線は観測された端点を結ぶだけで、欠損コストを埋めたり、アクティビティがなかったことを示したりするものではありません。
