Claude Code + Codex · 安装

构建并部署完整服务

从 Git 源代码开始。在连接编码客户端之前，先部署仪表板、ClickHouse 及其架构，以及 OTel 数据采集路径。

更新于 2026 年 11 月 10 日 · 基于源代码的说明；请核实所选版本和目标环境。

克隆并构建 · 数据库架构 · OTel 后端 · 托管选项 · 客户端跟踪

必须安装的组件

本指南不依赖已发布的应用程序 .tar.gz。请克隆仓库并构建其 Docker 镜像。可选的设备软件包由已安装的仪表板生成；它们不会安装后端。

组件用途和来源
仪表板应用dashboard/Dockerfile 将 React 和 Express 构建到一个镜像中，在 8080 端口提供 UI 和 API。它不会运行 ClickHouse 或 OTel Collector。
ClickHouse 和架构持久化数据库、遥测表、物化视图和迁移账本。请根据部署选择单节点或副本架构。
OTel Collector单独运行的 Collector 接收日志、指标和跟踪，应用仓库中的筛选和转换规则，并写入已准备好的表。
身份验证和密钥OIDC 或配置的 Basic 身份验证、HTTPS 访问、私有数据库连接、独立的读取/写入/管理凭据，以及受保护的密钥挂载。
客户端采集Claude Code/Codex 导出器和本地 Collector，或由组织者管理的采集路径。部署后端不会更改用户的客户端设置。

请先安装 Git 和带 buildx 的 Docker。对于 EKS，还需准备组织部署前提条件中说明的现有集群依赖项、Terraform、AWS CLI 和 kubectl。

1. 克隆一个版本并构建镜像

将 CCDASH_RELEASE 设置为实际发布的 vX.Y.Z 版本标签。根据运行时选择平台；提供的 EKS 部署使用 linux/arm64。

: "${CCDASH_RELEASE:?Set a published vX.Y.Z release tag}"
CCDASH_PLATFORM=linux/arm64
git clone https://github.com/Atom-oh/claude-code-usage-dashboard.git
cd claude-code-usage-dashboard
git checkout --detach "$CCDASH_RELEASE"
CCDASH_REVISION=$(git rev-parse HEAD)
docker build --platform "$CCDASH_PLATFORM" \
  --build-arg APP_REVISION="$CCDASH_REVISION" \
  --tag "ccdash:$CCDASH_RELEASE" dashboard

构建上下文是 dashboard/，而不是仓库根目录。对于 x86 运行时，请选择 linux/amd64，并单独验证该部署。若在不同架构上构建，则需要配置跨平台构建器。

生产环境请遵循经过审核的构建、检查、发布到镜像仓库和上线流程。请保留版本、源代码修订版本和镜像摘要；本地构建成功不等于部署完成。

2. 在开始采集之前准备 ClickHouse

首先配置持久化 ClickHouse 存储以及备份/恢复机制。创建仪表板只读账户、具有所需导出器授权的写入账户，以及管理迁移的账户。架构文件不会为你配置生产环境用户。

提供的账户策略授予 otel_reader 对 claude_code.* 的 SELECT 权限。otel_ingest 账户需要对 claude_code.* 的 INSERT 权限，以及对物化视图源数据读取所需的 claude_code.otel_metrics_sum 的 SELECT 权限；仅有 INSERT 可能导致采集失败。请限制账户网络，并参照仓库中的 ClickHouse 账户策略配置受保护的凭据。

部署方式架构路径
全新单节点 / 本地评估clickhouse-schema.sql：非复制表、视图、汇总表和当前迁移保护规则。包含 Claude 遥测数据，以及专用的 Codex 指标/成本/诊断表。
全新副本 EKS 安装使用 infra/schema.tf 中生成的契约和 schema-init Job，配合 infra/files/clickhouse-schema-replicated.sql。需要已声明的集群/Keeper 拓扑和预期副本。
现有安装检查表、账本和历史数据。根据对应的运行手册，仅应用所需的编号迁移；不要在升级时重放引导初始化。

对于 EC2/Docker，请先创建专用桥接网络和持久数据卷。准备受保护的 users.d XML，其中包含 reader/ingest/admin 账户、受限网络且不允许匿名默认访问；还要准备管理员客户端配置。针对所选版本验证并固定 ClickHouse 镜像；本地 Compose 版本可作为起始参考。CLICKHOUSE_SKIP_USER_SETUP=1 会保留已准备的账户配置；请先验证身份验证和网络限制。以下命令会启动数据库，但不会公开其端口：

: "${CCDASH_NETWORK:?Set the prepared private Docker network}"
: "${CCDASH_CH_CONTAINER:?Set the ClickHouse container name}"
: "${CCDASH_CH_IMAGE:?Set the reviewed ClickHouse image including its sha256 digest}"
: "${CCDASH_CH_DATA_VOLUME:?Set the prepared persistent data volume}"
: "${CCDASH_CH_USERS_DIR:?Set the protected users.d configuration directory}"
: "${CCDASH_CH_ADMIN_CONFIG:?Set the protected admin client configuration file}"
docker run -d --name "$CCDASH_CH_CONTAINER" --restart unless-stopped \
  --network "$CCDASH_NETWORK" --network-alias clickhouse.internal \
  --env CLICKHOUSE_SKIP_USER_SETUP=1 \
  --mount "type=volume,src=$CCDASH_CH_DATA_VOLUME,dst=/var/lib/clickhouse" \
  --mount "type=bind,src=$CCDASH_CH_USERS_DIR,dst=/etc/clickhouse-server/users.d,readonly" \
  --mount "type=bind,src=$CCDASH_CH_ADMIN_CONFIG,dst=/run/ccdash-admin/client.xml,readonly" \
  "$CCDASH_CH_IMAGE"

等待 ClickHouse 启动，并使用挂载的管理员客户端配置进行身份验证。对于下方的架构命令，其容器内路径是 /run/ccdash-admin/client.xml。在此网络上，将 clickhouse.internal 用作应用和 Collector 的数据库主机。镜像和挂载的配置必须与运行时架构及文件读取权限相匹配。

对于全新、空白且非复制的数据库，请将 CCDASH_CH_CONTAINER 设置为正在运行的 ClickHouse 容器，并将 CCDASH_CH_CLIENT_CONFIG 设置为容器内受保护的管理员客户端配置路径。将持久存储挂载到 /var/lib/clickhouse，在开放写入采集前配置用户，并确保 8123/9000 端口保持私有。下方不包含密码。

: "${CCDASH_CH_CONTAINER:?Set the prepared ClickHouse container name}"
: "${CCDASH_CH_CLIENT_CONFIG:?Set the mounted admin client configuration path}"
docker exec -i "$CCDASH_CH_CONTAINER" \
  clickhouse-client --config-file "$CCDASH_CH_CLIENT_CONFIG" \
  --multiquery < clickhouse-schema.sql

docker exec "$CCDASH_CH_CONTAINER" clickhouse-client \
  --config-file "$CCDASH_CH_CLIENT_CONFIG" \
  --query "SELECT name FROM system.tables WHERE database='claude_code' ORDER BY name"

验证 otel_logs、otel_traces、Claude 指标表、全部四个 Codex 指标表、视图和 schema_migrations。Collector 使用 create_schema: false；它无法补齐缺失的表。迁移 003 要求逐条语句执行汇总数据切换。启用类型化读取还需要验证历史数据/实时数据覆盖情况，光有表并不足够。

现有的 dashboard/docker-compose.yml 会初始化全新的本地 ClickHouse 卷和合成种子数据。它使用开发环境身份验证，且不包含 OTel Collector 服务。它是评估起点，并非完整的生产安装；现有卷不会重新初始化。

架构生命周期和迁移顺序 · 启用 Codex 成本读取

3. 安装 OTel 后端

运行包含 ClickHouse exporter 和所需处理器的 Collector 发行版。对于可选的设备令牌路径，dashboard/collector/generated/central.yaml 是仓库中的私有中央接收器策略；请使用 infra/device_ingest.tf 中经过审核且以摘要固定的 Contrib 镜像。

  1. 将中央 YAML 挂载为 Collector 配置。设置 CH_HOST、CH_PORT（原生端口）、CH_DB=claude_code、CH_USER，以及相应的 CLAUDE_ENABLED/CODEX_ENABLED 标志。
  2. 将 ClickHouse 写入凭据以只读方式挂载到 /var/run/ccdash-clickhouse/CH_PASSWORD，并将内部接收器 bearer token 以只读方式挂载到 /var/run/ccdash-ingest/token。确保容器用户能够读取这些文件。不要将此内部令牌分发给客户端。
  3. 保持接收器端口 4318 和健康检查端口 13133 为私有。生成的中央策略使用带 bearer 身份验证的 OTLP HTTP，以及私有原生 ClickHouse 连接。跨边界连接需要使用适当的 TLS 策略。
  4. 启用所有必需的管道：Claude 指标/日志/跟踪以及 Codex 指标/日志/跟踪。Codex 指标管道写入其专用表；日志和跟踪使用共享表，并保留客户端身份信息。
  5. 若要启用设备采集，请配置仪表板的 OIDC 访问控制、DynamoDB 设备注册表、运行时 IAM 权限、INGEST_ENABLED=1、INGEST_TOKEN_TABLE、INGEST_UPSTREAM_URL 和 INGEST_UPSTREAM_TOKEN_FILE。后端会将通过身份验证的设备请求转发到私有接收器。

对于由组织者管理的客户端，collector-config.yaml 和 user-data.sh 描述的是另一条从本地 Collector 到 ClickHouse 的路径，其中包含特定于部署的凭据和端点。不要原样复制配置来混用这两条路径。

在 EC2/Docker 主机上，准备一个可访问 ClickHouse 的私有 Docker 网络、一个非密钥类 Collector 环境文件，以及两个受保护的密钥文件。选择 infra/device_ingest.tf 中以摘要固定的镜像；这些文件必须可供该镜像的运行时用户读取。仪表板可在此网络上访问中央接收器；不会向主机发布 OTLP 或健康检查端口：

: "${CCDASH_NETWORK:?Set the existing private Docker network}"
: "${CCDASH_COLLECTOR_IMAGE:?Set the pinned contrib image including its sha256 digest}"
: "${CCDASH_COLLECTOR_ENV_FILE:?Set the prepared nonsecret Collector environment file}"
: "${CCDASH_INGEST_SECRET_DIR:?Set the protected directory containing token}"
: "${CCDASH_INGEST_CH_SECRET_DIR:?Set the protected directory containing CH_PASSWORD}"
docker run -d --name ccdash-otel --restart unless-stopped \
  --network "$CCDASH_NETWORK" \
  --env-file "$CCDASH_COLLECTOR_ENV_FILE" \
  --mount "type=bind,src=$PWD/dashboard/collector/generated/central.yaml,dst=/etc/otelcol-contrib/config.yaml,readonly" \
  --mount "type=bind,src=$CCDASH_INGEST_SECRET_DIR,dst=/var/run/ccdash-ingest,readonly" \
  --mount "type=bind,src=$CCDASH_INGEST_CH_SECRET_DIR,dst=/var/run/ccdash-clickhouse,readonly" \
  "$CCDASH_COLLECTOR_IMAGE" --config=/etc/otelcol-contrib/config.yaml

对于此网络，请将应用的上游地址设置为 http://ccdash-otel:4318，并在 INGEST_UPSTREAM_TOKEN_FILE 处挂载相同的内部 bearer token。此令牌不同于每位用户的设备令牌。提供的中央队列位于内存中；请根据运行要求设计持久化/重试机制并监控数据丢失。

4. 配置并启动仪表板

启动镜像前，请提供数据库连接和身份验证设置。以下是非密钥类配置模板；请将示例端点、签发方、客户端 ID 和群组名称替换为部署环境中的值。

CH_URL=http://clickhouse.internal:8123
CH_DB=claude_code
CH_USER=otel_reader
CH_PASSWORD_FILE=/run/ccdash-secrets/CH_PASSWORD
CLAUDE_ENABLED=true
CODEX_ENABLED=true
AUTH_MODE=oidc
APP_PUBLIC_URL=https://dashboard.example.com
OIDC_ISSUER=https://issuer.example.com
OIDC_CLIENT_ID=YOUR_APP_CLIENT_ID
OIDC_ROLE_GROUPS={"viewer":["YOUR_VIEWER_GROUP"],"analyst":["YOUR_ANALYST_GROUP"],"admin":["YOUR_ADMIN_GROUP"]}
OIDC_CLIENT_SECRET_FILE=/run/ccdash-secrets/OIDC_CLIENT_SECRET
SESSION_SECRET_FILE=/run/ccdash-secrets/SESSION_SECRET

通过平台的密钥机制配置所引用的三个密钥文件，并以只读方式挂载。SESSION_SECRET 必须是经过 base64url 编码的 32 字节随机密钥。请保持文件内容和权限准确无误；运行时镜像使用非 root 的 node 用户。在 EC2 上，在容器配置中使用相同的绝对挂载路径。在 ECS/EKS 上，实施相应的任务/Pod 密钥传递方式。面向公网的部署不要启用不安全的开发环境身份验证。

在 EC2/Docker 主机上准备好 CCDASH_ENV_FILE 和 CCDASH_SECRET_DIR 后，可通过单独配置的 HTTPS 反向代理运行应用：

: "${CCDASH_RELEASE:?Set the built release tag}"
: "${CCDASH_ENV_FILE:?Set the prepared nonsecret environment file}"
: "${CCDASH_SECRET_DIR:?Set the runtime-readable protected secret directory}"
: "${CCDASH_NETWORK:?Set the existing private Docker network}"
docker run -d --name ccdash --restart unless-stopped \
  --network "$CCDASH_NETWORK" \
  --publish 127.0.0.1:8080:8080 \
  --env-file "$CCDASH_ENV_FILE" \
  --mount "type=bind,src=$CCDASH_SECRET_DIR,dst=/run/ccdash-secrets,readonly" \
  "ccdash:$CCDASH_RELEASE"

要启用设备采集，还需在应用运行时配置中添加内部令牌文件挂载，以及上一步中的 INGEST_* 设置。此基础应用命令本身不会配置设备注册表，也不会启用采集。

OIDC 和角色配置 · 环境变量参考

选择 EC2、ECS、EKS 或 Lambda 移植方案

选项部署形态仓库支持和剩余工作
EC2 + Docker在私有主机或网络上运行仪表板、Collector 和持久化 ClickHouse。使用持久数据库/队列存储和 HTTPS 入口。仓库提供应用镜像和单节点架构。主机/服务生命周期、密钥、数据库用户、网络路由和备份需要自行准备。Workshop user-data 脚本配置的是客户端采集，而非整个后端。
ECS / Fargate将应用和 Collector 镜像发布到 ECR；运行独立服务或适当的 sidecar。使用私有网络，并单独管理持久化 ClickHouse 安装。未提供 ECS 任务/服务模板。请定义任务/执行角色、密钥传递、CPU/内存、镜像架构、健康检查和服务连接。不要依赖临时任务文件系统来存放数据库或持久队列。
EKS使用现有集群、ClickHouse/Keeper 运算符和持久卷；通过仓库提供的 Terraform 部署应用和可选的中央接收器。infra/ 会复用集群/VPC。请准备运算符、Karpenter、CSI/存储、DNS/证书、IAM 和密钥，然后执行 plan/apply、验证 schema-init、发布经过审核的镜像并上线。它不会创建所有前提资源。
Lambda将 HTTP 应用移植到兼容 Lambda 的运行时/适配器。让 ClickHouse 和采集 Collector 继续运行在持久化外部服务上。当前 Docker 镜像会启动 Express，但没有 Lambda handler/runtime 集成。未提供现成的 Lambda 部署方案。适配后请验证身份验证 Cookie、流式传输/chat、超时、网络和设备采集；仅选择 Lambda 并不会安装此技术栈。

官方平台参考资料：EC2 · ECS/Fargate 任务定义 · EKS 应用部署 · Lambda 镜像/运行时要求。

5. 连接客户端日志、指标和跟踪

后端正常运行后，配置每个客户端的本地 Collector 和导出器目标。对于设备路径，分析师/管理员可在已部署的仪表板中注册设备。如果无法下载，请直接使用源代码安装程序；仍需已安装的后端和已签发的设备令牌。

: "${CCDASH_INGEST_ENDPOINT:?Set the deployed HTTPS dashboard URL ending in /api/ingest}"
: "${CCDASH_USER_ID:?Set the intended telemetry attribution ID}"
python3 dashboard/collector/install.py install \
  --endpoint "$CCDASH_INGEST_ENDPOINT" --user-id "$CCDASH_USER_ID"

安装程序在 macOS/Linux 上需要 Python 3.9+，并会以私密方式提示输入令牌。在 Linux 上，运行 sudo loginctl enable-linger "$USER"，以便注销/重启后服务仍能运行，然后以普通用户身份安装。安装程序会下载并验证 Collector 二进制文件；此命令不会配置仪表板、数据库或中央接收器。设备所有者不会自动成为发出的遥测数据身份。

  • Claude Code：启用遥测和增强遥测，设置 OTEL_TRACES_EXPORTER=otlp，并将本地 OTLP gRPC 目标设为 4317 端口。
  • Codex：分别配置 [otel] 下的 exporter、metrics_exporter 和 trace_exporter；将本地 OTLP HTTP 目标设为 4318 端口，并设置 log_user_prompt=false。

重启两个客户端并生成新活动，然后沿着用户 → 趋势时间桶 → 任务 → Task Trace查看。跟踪中不会回填此前的活动。要查看 Codex 诊断跨度，请打开 Analytics 的 Trace 选项卡。

现有设备和数据库

设备迁移期间，请保留客户端私有备份和导出器队列。请遵循受支持的 macOS/Linux 迁移流程，不要停止未知服务。数据库升级依照架构运行手册单独执行，与客户端安装和应用上线分开进行。

6. 验证每个边界

  1. 检查 /healthz 和由 ClickHouse 支持的 /readyz，然后进行身份验证并查看安装/架构诊断信息。
  2. 确认预期表、迁移账本、视图、数据库授权和 Collector 写入成功；架构存在本身并不能证明历史数据已就绪。
  3. 生成新的客户端活动，并验证其以预期身份存储了日志、指标和跟踪。Collector 进程运行或设备收到回执，都不能证明数据已持久化。
  4. 检查所选用户的用量和 Task Trace。Codex 跟踪/指标观测数据仅用于诊断，不能再计入一份成本总额。
