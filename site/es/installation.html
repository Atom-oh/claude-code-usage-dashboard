Claude Code + Codex · Instalación

Construya e implemente el servicio completo

Empiece con el código fuente de Git. Implemente el panel, ClickHouse y su esquema, además de una ruta de recopilación OTel antes de conectar los clientes de programación.

Actualizado el 14 de noviembre de 2026 · Instrucciones basadas en el código fuente; verifique la versión seleccionada y el entorno de destino.

Clonar y compilar · Esquema de la base de datos · Backend OTel · Opciones de alojamiento · Trazas de clientes

Qué debe instalar

Esta guía no depende de que haya una imagen de aplicación publicada .tar.gz. Clone el repositorio y compile su imagen Docker. Los paquetes opcionales para dispositivos los genera un panel ya instalado; no instalan el backend.

ComponentePropósito y origen
Aplicación del paneldashboard/Dockerfile compila React y Express en una sola imagen que sirve la interfaz y la API en el puerto 8080. No ejecuta ClickHouse ni un Collector OTel.
ClickHouse y esquemaBase de datos persistente, tablas de telemetría, vistas materializadas y registro de migraciones. Elija el esquema de nodo único o replicado para su implementación.
Collector OTelUn Collector independiente recibe registros, métricas y trazas, aplica los filtros y transformaciones del repositorio y escribe en las tablas preparadas.

Recopilación de clientesExportadores de Claude Code/Codex y un Collector local o una ruta de recopilación administrada por el organizador. La implementación del backend no cambia la configuración de los clientes de los usuarios.

Primero instale Git y Docker con buildx. Para EKS, prepare también las dependencias del clúster existente, Terraform, AWS CLI y kubectl que se describen en requisitos previos de implementación de la organización.

1. Clone una versión y compile la imagen

Defina CCDASH_RELEASE con la etiqueta de versión publicada vX.Y.Z. Elija la plataforma que coincida con su entorno de ejecución; la implementación EKS proporcionada usa linux/arm64.

: "${CCDASH_RELEASE:?Set a published vX.Y.Z release tag}"
CCDASH_PLATFORM=linux/arm64
git clone https://github.com/Atom-oh/claude-code-usage-dashboard.git
cd claude-code-usage-dashboard
git checkout --detach "$CCDASH_RELEASE"
CCDASH_REVISION=$(git rev-parse HEAD)
docker build --platform "$CCDASH_PLATFORM" \
  --build-arg APP_REVISION="$CCDASH_REVISION" \
  --tag "ccdash:$CCDASH_RELEASE" dashboard

El contexto de compilación es dashboard/, no la raíz del repositorio. Para un entorno de ejecución x86, seleccione linux/amd64 y valide esa implementación por separado. Para compilar en otra arquitectura se requiere un generador multiplataforma configurado.

Para producción, siga el procedimiento revisado de compilación, inspección, publicación en el registro e implementación. Conserve la versión, la revisión del código fuente y el digest de la imagen; no considere que una compilación local correcta sea una implementación.

2. Prepare ClickHouse antes de iniciar la ingesta

Primero aprovisione almacenamiento persistente de ClickHouse y configure las copias de seguridad y la recuperación. Cree una cuenta de solo lectura para el panel, una cuenta de ingesta con los permisos necesarios para los exportadores y una cuenta administrativa para las migraciones. El archivo de esquema no aprovisiona las cuentas de producción.

La política de cuentas proporcionada concede otel_reader SELECT sobre claude_code.*. La otel_ingest requiere INSERT en claude_code.* y SELECT en claude_code.otel_metrics_sum para leer el origen de la vista materializada; INSERT por sí solo puede hacer que falle la ingesta. Restrinja las redes de las cuentas y configure las credenciales protegidas tomando como referencia la política de cuentas de ClickHouse del repositorio.

ImplementaciónRuta del esquema
Nodo único nuevo / evaluación localclickhouse-schema.sql: tablas no replicadas, vistas, agregaciones y protecciones actuales de migración. Incluye telemetría de Claude y tablas específicas para métricas, costos y diagnósticos de Codex.
Instalación EKS replicada nuevainfra/files/clickhouse-schema-replicated.sql con el contrato generado y el Job de inicialización de esquema en infra/schema.tf. Requiere la topología de clúster/Keeper declarada y las réplicas previstas.
Instalación existenteInspeccione las tablas, el registro y los datos históricos. Aplique solo las migraciones numeradas necesarias y siga sus procedimientos operativos; no vuelva a ejecutar el inicialización como si fuera una actualización.

Para EC2/Docker, prepare estos requisitos antes de iniciar ClickHouse:

  • Una red puente privada y un volumen de datos persistente.
  • Protegido users.d XML para las cuentas de lectura, ingesta y administración, redes restringidas, acceso anónimo predeterminado deshabilitado y configuración de cliente administrador.
  • Una imagen de ClickHouse cualificada y fijada por digest; la versión de Compose local es solo una referencia inicial.

CLICKHOUSE_SKIP_USER_SETUP=1 conserva esa configuración de cuentas. Primero valide la autenticación y las restricciones de red. Este comando no publica los puertos de la base de datos:

: "${CCDASH_NETWORK:?Set the prepared private Docker network}"
: "${CCDASH_CH_CONTAINER:?Set the ClickHouse container name}"
: "${CCDASH_CH_IMAGE:?Set the reviewed ClickHouse image including its sha256 digest}"
: "${CCDASH_CH_DATA_VOLUME:?Set the prepared persistent data volume}"
: "${CCDASH_CH_USERS_DIR:?Set the protected users.d configuration directory}"
: "${CCDASH_CH_ADMIN_CONFIG:?Set the protected admin client configuration file}"
docker run -d --name "$CCDASH_CH_CONTAINER" --restart unless-stopped \
  --network "$CCDASH_NETWORK" --network-alias clickhouse.internal \
  --env CLICKHOUSE_SKIP_USER_SETUP=1 \
  --mount "type=volume,src=$CCDASH_CH_DATA_VOLUME,dst=/var/lib/clickhouse" \
  --mount "type=bind,src=$CCDASH_CH_USERS_DIR,dst=/etc/clickhouse-server/users.d,readonly" \
  --mount "type=bind,src=$CCDASH_CH_ADMIN_CONFIG,dst=/run/ccdash-admin/client.xml,readonly" \
  "$CCDASH_CH_IMAGE"

Espere a que ClickHouse se inicie y autentíquese con la configuración de cliente administrador montada. Para el comando de esquema que sigue, la ruta dentro del contenedor es /run/ccdash-admin/client.xml. Use clickhouse.internal como host de base de datos para la aplicación y el Collector en esta red. La imagen y las configuraciones montadas deben coincidir con la arquitectura de ejecución y los permisos de lectura de archivos.

Para una base de datos nueva, vacía y no replicada, defina CCDASH_CH_CONTAINER como el contenedor de ClickHouse en ejecución y CCDASH_CH_CLIENT_CONFIG como la ruta de la configuración protegida de cliente administrador dentro de él.

: "${CCDASH_CH_CONTAINER:?Set the prepared ClickHouse container name}"
: "${CCDASH_CH_CLIENT_CONFIG:?Set the mounted admin client configuration path}"
docker exec -i "$CCDASH_CH_CONTAINER" \
  clickhouse-client --config-file "$CCDASH_CH_CLIENT_CONFIG" \
  --multiquery < clickhouse-schema.sql

docker exec "$CCDASH_CH_CONTAINER" clickhouse-client \
  --config-file "$CCDASH_CH_CLIENT_CONFIG" \
  --query "SELECT name FROM system.tables WHERE database='claude_code' ORDER BY name"

Verifique otel_logs, otel_traces, las tablas de métricas de Claude, las cuatro tablas de métricas de Codex, las vistas y schema_migrations. El Collector usa create_schema: false; no puede crear las tablas que faltan. La migración 003 requiere cambiar las agregaciones instrucción por instrucción. La activación de lectura tipada también exige verificar la cobertura histórica y en tiempo real; no basta con que existan las tablas.

El dashboard/docker-compose.yml existente inicializa un volumen local nuevo de ClickHouse y carga datos sintéticos de ejemplo. Usa autenticación de desarrollo y no incluye un servicio Collector OTel. Es un punto de partida para evaluación, no una instalación de producción completa; los volúmenes existentes no se vuelven a inicializar.

3. Instale el backend OTel

Ejecute una distribución de Collector que incluya el exportador de ClickHouse y los procesadores necesarios. Para la ruta opcional con token de dispositivo, dashboard/collector/generated/central.yaml es la política del receptor central privado del repositorio; use la imagen Contrib revisada y fijada por digest de infra/device_ingest.tf.

  1. Monte el YAML central como configuración del Collector. Defina CH_HOST, CH_PORT (puerto nativo), CH_DB=claude_code, CH_USER y las opciones correspondientes CLAUDE_ENABLED/CODEX_ENABLED.
  2. Monte la credencial de ingesta de ClickHouse en /var/run/ccdash-clickhouse/CH_PASSWORD y el token bearer interno del receptor en /var/run/ccdash-ingest/token, en modo de solo lectura. Asegúrese de que el usuario del contenedor pueda leerlos. No distribuya este token interno a los clientes.
  3. Mantenga privados el puerto 4318 del receptor y el puerto 13133 de estado. La política central generada usa OTLP HTTP con autenticación bearer y una conexión nativa privada con ClickHouse. Las conexiones que cruzan límites requieren la política TLS adecuada.
  4. Habilite todas las canalizaciones necesarias: métricas/registros/trazas de Claude y métricas/registros/trazas de Codex. Las canalizaciones de métricas de Codex escriben en sus tablas específicas; los registros y las trazas usan tablas compartidas que conservan la identidad del cliente.
  5. Para la ingesta de dispositivos, configure la puerta OIDC del panel, el registro de dispositivos de DynamoDB, los permisos IAM de ejecución, INGEST_ENABLED=1, INGEST_TOKEN_TABLE, INGEST_UPSTREAM_URL y INGEST_UPSTREAM_TOKEN_FILE. El backend reenvía los dispositivos autenticados al receptor privado.

Para los clientes administrados por el organizador, collector-config.yaml y user-data.shdescriben una ruta separada desde un Collector local hasta ClickHouse, con credenciales y endpoints específicos de la implementación. No combine las dos rutas copiando una configuración sin modificarla.

En un host EC2/Docker, prepare una red Docker privada con acceso a ClickHouse, un archivo de entorno del Collector sin secretos y los dos archivos de secretos protegidos. Seleccione la imagen fijada por digest de infra/device_ingest.tf; los archivos deben ser legibles por el usuario de ejecución de esa imagen. El panel puede acceder al receptor central en esta red; no se publica ningún puerto OTLP ni de estado en el host:

: "${CCDASH_NETWORK:?Set the existing private Docker network}"
: "${CCDASH_COLLECTOR_IMAGE:?Set the pinned contrib image including its sha256 digest}"
: "${CCDASH_COLLECTOR_ENV_FILE:?Set the prepared nonsecret Collector environment file}"
: "${CCDASH_INGEST_SECRET_DIR:?Set the protected directory containing token}"
: "${CCDASH_INGEST_CH_SECRET_DIR:?Set the protected directory containing CH_PASSWORD}"
docker run -d --name ccdash-otel --restart unless-stopped \
  --network "$CCDASH_NETWORK" \
  --env-file "$CCDASH_COLLECTOR_ENV_FILE" \
  --mount "type=bind,src=$PWD/dashboard/collector/generated/central.yaml,dst=/etc/otelcol-contrib/config.yaml,readonly" \
  --mount "type=bind,src=$CCDASH_INGEST_SECRET_DIR,dst=/var/run/ccdash-ingest,readonly" \
  --mount "type=bind,src=$CCDASH_INGEST_CH_SECRET_DIR,dst=/var/run/ccdash-clickhouse,readonly" \
  "$CCDASH_COLLECTOR_IMAGE" --config=/etc/otelcol-contrib/config.yaml

En esta red, configure el upstream de la aplicación como http://ccdash-otel:4318 y monte el mismo token bearer interno en INGEST_UPSTREAM_TOKEN_FILE. Este token es distinto del token de dispositivo de cada usuario. La cola central proporcionada reside en memoria; diseñe la persistencia, los reintentos y la supervisión de pérdidas según sus requisitos operativos.

4. Configure e inicie el panel

Configure la conexión a la base de datos y los ajustes de autenticación antes de iniciar la imagen. La siguiente plantilla no contiene secretos; sustituya el endpoint, el emisor, el ID del cliente y los nombres de grupo de ejemplo por los valores de su implementación.

CH_URL=http://clickhouse.internal:8123
CH_DB=claude_code
CH_USER=otel_reader
CH_PASSWORD_FILE=/run/ccdash-secrets/CH_PASSWORD
CLAUDE_ENABLED=true
CODEX_ENABLED=true
AUTH_MODE=oidc
APP_PUBLIC_URL=https://dashboard.example.com
OIDC_ISSUER=https://issuer.example.com
OIDC_CLIENT_ID=YOUR_APP_CLIENT_ID
OIDC_ROLE_GROUPS={"viewer":["YOUR_VIEWER_GROUP"],"analyst":["YOUR_ANALYST_GROUP"],"admin":["YOUR_ADMIN_GROUP"]}
OIDC_CLIENT_SECRET_FILE=/run/ccdash-secrets/OIDC_CLIENT_SECRET
SESSION_SECRET_FILE=/run/ccdash-secrets/SESSION_SECRET

Prepare los secretos antes de iniciar el panel:

  • Aprovisione los tres archivos mencionados mediante el mecanismo de secretos de la plataforma y móntelos en modo de solo lectura.
  • Use una clave aleatoria de 32 bytes codificada en base64url para SESSION_SECRET. Conserve el contenido exacto y los permisos de lectura para el usuario no root node.
  • En EC2, conserve las rutas absolutas configuradas dentro del contenedor. En ECS/EKS, configure la entrega de secretos correspondiente a la tarea o el pod.

Mantenga deshabilitada la autenticación de desarrollo insegura en las implementaciones públicas.

Después de preparar CCDASH_ENV_FILE y CCDASH_SECRET_DIR en un host EC2/Docker, este comando ejecuta la aplicación detrás de un proxy inverso HTTPS configurado por separado:

: "${CCDASH_RELEASE:?Set the built release tag}"
: "${CCDASH_ENV_FILE:?Set the prepared nonsecret environment file}"
: "${CCDASH_SECRET_DIR:?Set the runtime-readable protected secret directory}"
: "${CCDASH_NETWORK:?Set the existing private Docker network}"
docker run -d --name ccdash --restart unless-stopped \
  --network "$CCDASH_NETWORK" \
  --publish 127.0.0.1:8080:8080 \
  --env-file "$CCDASH_ENV_FILE" \
  --mount "type=bind,src=$CCDASH_SECRET_DIR,dst=/run/ccdash-secrets,readonly" \
  "ccdash:$CCDASH_RELEASE"

Para habilitar la ingesta de dispositivos, añada también el montaje del archivo de token interno y los ajustes INGEST_* del paso anterior a la configuración de ejecución de la aplicación. Este comando básico de la aplicación no configura por sí solo el registro de dispositivos ni habilita la ingesta.

5. Conecte los registros, las métricas y las trazas de los clientes

Cuando el backend funcione, configure el Collector local de cada cliente y el destino del exportador. Para la ruta de dispositivos, un analista o administrador puede registrar un dispositivo en el panel implementado. Elija la plataforma del dispositivo, regístrelo y copie el comando de instalación. La terminal solicita el ID de atribución de telemetría y el token del dispositivo; el token no se incluye en el comando. Se requiere un backend instalado y un token de dispositivo emitido.

Instalación en dispositivos

macOS

: "${CCDASH_DASHBOARD_URL:?Set the deployed HTTPS dashboard origin}"
curl -fsSL "$CCDASH_DASHBOARD_URL/api/ingest/install.sh" | sh

Linux

: "${CCDASH_DASHBOARD_URL:?Set the deployed HTTPS dashboard origin}"
sudo loginctl enable-linger "$USER" &&
  curl -fsSL "$CCDASH_DASHBOARD_URL/api/ingest/install.sh" | sh

El script descarga el paquete usando el token bearer del dispositivo y luego ejecuta el instalador con un archivo de token privado. El token del dispositivo no autoriza el inicio de sesión interactivo en el panel.

Alternativa de instalación manual desde el código fuente

: "${CCDASH_INGEST_ENDPOINT:?Set the deployed HTTPS dashboard URL ending in /api/ingest}"
: "${CCDASH_USER_ID:?Set the intended telemetry attribution ID}"
python3 dashboard/collector/install.py install \
  --endpoint "$CCDASH_INGEST_ENDPOINT" --user-id "$CCDASH_USER_ID"

El instalador requiere Python 3.9 o posterior en macOS/Linux y solicita el token de forma privada. En Linux, ejecute sudo loginctl enable-linger "$USER" para mantener el servicio después de cerrar sesión o reiniciar; luego instale como usuario normal. Descarga y verifica el binario del Collector; este comando no aprovisiona el panel, la base de datos ni el receptor central. El propietario del dispositivo no se convierte automáticamente en la identidad de telemetría emitida.

  • Claude Code: CLAUDE_CODE_ENABLE_TELEMETRY=1 y CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1, OTEL_TRACES_EXPORTER=otlp, destino gRPC OTLP local en el puerto 4317.
  • Codex: entradas separadas [otel] exporter, metrics_exporter y trace_exporter; destinos HTTP OTLP locales en el puerto 4318 y log_user_prompt=false.

Reinicie ambos clientes, genere trabajo nuevo y siga la ruta usuario → período seleccionado → tarea → Traza de tareas. La actividad anterior no se incorpora retroactivamente a las trazas. Para los tramos de diagnóstico de Codex, abra la pestaña Trace de Analítica.

Dispositivos y bases de datos existentes

Durante la migración de dispositivos, conserve las copias de seguridad privadas de los clientes y las colas de los exportadores. Siga el procedimiento de migración compatible con macOS/Linux en lugar de detener un servicio desconocido. Las actualizaciones de la base de datos siguen el procedimiento operativo de esquema, independientemente de la instalación de clientes y el despliegue de la aplicación.

6. Verifique cada límite

  1. Compruebe /healthz y /readyz; después, autentíquese y examine los diagnósticos de instalación y esquema.
  2. Confirme las tablas previstas, el registro de migraciones, las vistas, los permisos de base de datos y que el Collector escriba correctamente; la existencia del esquema por sí sola no significa que haya datos históricos disponibles.
  3. Genere actividad nueva en el cliente y compruebe que los registros, las métricas y las trazas se almacenen con la identidad prevista. Un proceso Collector o la recepción de un dispositivo no demuestran que los datos persistan.
  4. Compruebe el uso del usuario seleccionado y su Traza de tareas. Las observaciones de trazas y métricas de Codex son diagnósticos y no deben sumar otro total de costo.
